# 协作原则

用户负责需求、架构取舍和验收；AI 负责实现、验证、审查及 Git 全过程，交付时交代分支和状态。

## 开工

- 一任务一分支一工作树，不与其他智能体共用。跨轮、改运行行为/共享接口或验证界面时，改文件前隔离；当场完成并提交的小改动可用主目录。拿不准就隔离。
- 从最新集成分支开工，优先用工具管理的工作树；所有读写和索引指向该树。命名、初始化和验收入口见 `.agents/project.md`。不把 node_modules 软链到主目录。
- 不 stash、覆盖、回退或顺手提交他人的改动。与并行任务改同一处或依赖其产出时，说明并建议排定顺序。
- 先读相关 SPEC 和代码。新的产品取舍、跨模块行为、公共契约、权限或持久数据变更，先说明方案、风险和验收方式并确认；已有授权不重问，低风险机械修改说明范围后直接做。
- 确认的设计先入 SPEC；大方案落 Plan，拆成可独立验收的步骤与提交，重构和新功能分开。点子按 ideas 规则记录，不自动开工。

## 验证与交付

- 文档查链接及一致性；样式验界面；后端行为跑针对性测试及 CLI 回归；共享基础设施、权限和数据变更扩大验证范围。优先真实链路、隔离数据，检查异常日志；不使用用户真实数据验证。
- 每次自审 diff；新功能、较大行为改动独立审查，工具不可用时结构化自审并说明限制。未执行的检查不得称通过。
- 阶段检查后主动提交，只含本任务；重大架构变化更新架构文档，相关想法状态随提交更新。依赖或落盘格式变化交付时点明，迁移建议先备份。
- 交付说明效果、验法、证据、限制和状态；保留工作树，用户明确说合才合。验收修补追加提交，不改已验记录。
- 交付和 Git 操作前读 `.agents/workflow.md`，执行变基、合入、标签和清理细则。合入后撤销用 revert，不改写集成分支历史。

不做无关重构、脆弱关键词分支或平行概念映射。复用既有分类与共享类型，不造第二个真相源；类型位置见项目架构。
