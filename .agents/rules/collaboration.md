# 协作开发规范

用户负责：需求定义、架构决策、验收。AI 负责：编码、测试、代码审查，以及这一路改动在 Git 上的全过程——开分支、开工作树、提交、合入、收尾。

用户常同时开好几个智能体，各做一件事，做完由他一个人很快验收。**用户不需要记住任何一路改动的 Git 状态**：哪棵树、做完没有、合没合，都由那条对话自己交代清楚。

本机可用 GitHub CLI（`gh`）。

## 规则入口与适用范围

所有编辑器先读取根目录 `AGENTS.md`，按其清单加载必读规则和任务相关文档；它也定义权威来源与工具降级方式。Cursor 自动注入的规则无需重复读取，其他文件不能假定会自动展开。每次新对话建立架构地图，相关专题在动手前完整阅读。

## 并行开发：一路改动一个现场

主目录指 Git 主工作树（用 `git worktree list` 识别），本项目检出 `develop`，是用户每天在跑、在验收的那份；热重载会把目录里的任何改动立刻卷进他眼前的应用。

- **一路改动 = 一条对话 = 一条分支 = 一棵工作树**，两个智能体不共用一棵树。能并行多少路看用户验得过来多少；要改同一块代码、或要用到另一路产出的，告诉用户，建议等那一路合进去再开——工作树只把冲突推迟到合入时。
- **什么时候开**：要跨轮的（等方案确认、等测试、等用户回话）、涉及运行行为或共享接口的、要起界面验证的，动手改第一个文件之前开。当场改完、当场提交的小改动可以留在主目录。拿不准就开。
- **怎么开**：从最新集成分支创建具名分支和独立工作树，优先使用当前工具管理的工作树；命名和验收入口见 `.agents/project.md`。工具支持时把对话关联到新工作树，否则所有操作明确指定其绝对目录；读写、终端和代码索引都指向同一棵树。合回只走「用户说合才合」。
- **初始化**：Cursor 建的树会按 `.cursor/worktrees.json` 自动初始化；手动建的进树后跑 `bash .cursor/setup-worktree-unix.sh`（写时复制克隆依赖，几秒钟）。不要把 `node_modules` 软链到主目录：树里重装会改到用户正在跑的那份。改了依赖的，合入时告诉用户主目录要重新安装。
- **跑起来验证**：命令行回归直接在树里跑。智能体看界面一律用 `scripts/ui-e2e/launch.mjs` 的 `launchApp` 加临时数据目录；不起 `npm run dev`、不跑 `review`——那是用户验收用的，会用他的真实数据在他面前起窗口。
- **用户怎么验**：`review` 列出每一路，`review <名字>` 起那一路（窗口和 Dock 上有「验收」标记，用他的真实数据；同一时间只开一个开发进程），`review --cli <名字> [一句话]` 在那一路跑命令行（进沙箱、不占端口）。没装短命令的机器用 `npm run review` / `npm run review:cli`。
- **变基**：别的分支合进 `develop`，正在做的树不必跟着变基，合入前变基一次就够。只在要用到刚合进去的东西、改的是同一块、或这条线已拖了好几天时提前变基，挑刚提交完的时候做。分支尽量当天开当天合，大功能拆成能各自合进去的几步。
- **主目录里别人的未提交改动不碰**：不 stash、不 checkout、不 reset，也不顺手提交。唯一例外是 `docs/ideas.md`，见「用户说合才合」。

## 开发流程

1. **点子先入想法本**：来不及做的点子记进 `docs/ideas.md`，不因此开工（见 `ideas.md`）
2. **先理解再动手**：改动前读相关代码和对应 SPEC 的设计目标（还没有 SPEC 的先写设计目标）；摸底用 CodeGraph
3. **大改动先出方案**：涉及新的产品取舍、跨模块行为变化、公共契约、权限或持久数据变更的，先说明范围、方案、风险和验收方式，用户确认后再编码；文件数量仅作提示，不作为门槛。已确认的方向不重复确认，低风险机械修改说明范围后直接做；大改动落成 plan 文档（命名与完成标记见 `spec-driven.md`；暂缓的文首写「未完成（暂缓）」、不加 `done-`）。讨论确认的设计先写进 SPEC 再改代码
4. **有推荐就自己定**：已有清楚推荐的按推荐做，做完说一声选了哪条。只在需求说不清、做错很难回头、或只有用户知道答案（产品取舍、要不要上线、对外承诺）时才问
5. **积极提交**：一个阶段做完并检查过，即可提交，不需要等用户开口。

## 改动完成后必须做

1. **跑测试**：按风险验证：纯文档检查链接、命令及规则一致性；样式改动验证受影响界面；后端行为改动跑针对性验证和 `bash electron/cli/test-cli.sh --no-ai`；共享类型、公共基础设施、权限或数据迁移扩大到受影响链路。具体命令见 cli-testing 技能，记录未执行检查及原因
2. **能端到端就端到端**：回归保的是「原来能用的没坏」，单测保的是「在我理解的模型下实现是对的」；bug 常出在理解本身就错了，只有让真东西跑起来才露头——真实数据的副本、真起几个进程、整条链路走一遍。别只看断言，日志里的警告、对不上的数往往就是模型与现实不符
3. **代码审查**：每次交付自审 diff；新功能或较大行为改动按 claude-review 技能做独立审查，高风险改动重点核查权限、兼容性和失败路径。工具不可用时执行结构化自审并披露限制，不把调用模型当成通过证明
4. **文档**：新增服务或重大重构后更新 `docs/architecture.md`；对得上的想法本条目随代码一起提交
5. **交卷与合入**：按下一节

## 交卷、合入与收尾

1. **跟上最新 `develop`**：变基后按受影响范围重跑检查；纯文档只需文档检查。机械冲突（两边各加一行、各加一条）自己解；意图冲突（两边为不同目的改了同一段逻辑，或合得进去但合起来不对）问用户。锁文件冲突用重新安装生成。想法本里的提交哈希变基后再补。
2. **交卷，等用户验**：工作树保留，不合。最后一条消息先讲用户能感知的结果和要他验什么，再讲测了什么、要注意什么；实现细节只在用户要看时给。验收开始后修补一律追加新提交。状态变了就用 `git config branch.<分支>.description "<状态那一句>"` 记下，`review` 列表读它。带数据迁移或改了落盘格式的，点明并建议先备份——切回 `develop` 可能读不了。
3. **用户说合才合**：在主目录 `git merge --no-ff`，标题写「合入 <分支>：这一批干了什么」，下面一两句写用户能感知的变化（`git log --first-parent` 读下来就是更新记录）；不压缩。合完打两个附注标签（`git tag -a`，说明写「这一批的基点/结尾：<名字>」）：变基完成、合入前记录 `git merge-base develop HEAD` 作为批次基点；将该基点打上 `🟡开始/<名字>`，合并提交上 `🟢结束/<名字>`（黄、绿两个符号是为了在 GitHub Desktop 的灰色标签里一眼分出开头结尾），开始与结束之间的差异表示整批改动；标签只用于定位，不代表测试通过。名字是分支名去掉 `feat/`、`codex/` 等前缀，重名时加日期或编号，不覆盖既有标签。标签不单独推，用户推 `develop` 时随之上 GitHub（仓库设了 `push.followTags`，没设的先设上；这一设置会带上所有附注标签，不想公开的检查点用轻量标签）。交卷后 `develop` 又动了就先变基再测。主目录有未提交改动挡住合并：只有 `docs/ideas.md` 的，单独提交成「想法本：<记了什么>」再合（写到一半的条目提交了也无妨，记的那边接着写、再提交即可）；有别的文件，停下告诉用户是哪些。合入会让用户的应用热重载，说一声。几路同时批准时，先合改共用接口、类型、数据格式的，试验性的最后。
4. **收尾**：拆树前先将对话工作目录或关联工作树切回主目录；没有切换工具时不要删除当前对话仍依赖的目录，明确说明待清理状态。合进去的，拆树删分支；先不上线的，拆树留分支（想法本挂分支名）；不要了的，问过再删；有未提交改动的树不拆。

每一路对话的最后一条消息，末尾单起一行写状态；支持修改标题的工具里同时更新对话标题；不支持时靠分支描述和交付状态，让对话列表准确反映每一路走到哪。状态一变就改，不等收工。下面每条后面括号里是标题前缀：

- `状态：还在做`（正在做什么）——（不加前缀）
- `状态：等你确认：……`——【待确认】。等用户拍板才往下做：方案、选哪条路、只有用户知道的问题。写清确认什么、确认后接着做什么。和「等你验」不同：这时活还没干完
- `状态：等你验，验过说「合」`——【待验】。下面紧跟能直接复制运行的命令块：界面 `review <名字>`，命令行 `review --cli <名字> <要试的那句话>`，直接改在主目录的写要跑的命令（比如重启 `npm run dev`）。先关什么、在哪个目录跑都写进去。要在应用里对智能体说话才能验的，命令块前先给验证用的提示词，单独放进能直接复制的块里，一句一块，说明各验什么
- `状态：卡住了，需要你……`——【卡住】。要用户动手才做得下去：登录、授权、装东西、查不出来的报错
- `状态：已合入 develop`——【已合入】
- `状态：留在分支 feat/xxx，没合`（为什么）——【留分支】
- `状态：已完成`——【已完成】。没有要合入的活做完了：查清原因、调研完、出完报告

「已合入」「已完成」只在那一刻的消息里写一次；之后只是答问题、没有新改动的回复不写状态行，免得像又办完了一批；又动手改了，按新的状态写。

标题写成「<前缀><这一路做什么>」，和对话用同一种语言：Cursor 自动起的常是英文，弄清这条对话要做什么之后，用对话的语言改成一句简短的标题。

验收不通过，就在原来的工作树里接着改、再交卷。合进去又要撤，撤回那个合并提交，不改写 `develop` 的历史。用户问「各路怎么样了」，把所有工作树和没合入的分支盘一遍，用人话说清每一路在哪一步。

## 大功能额外要求

- 拆成多个可独立验证的提交；大 plan 先列「任务拆解」（原子任务 + 每步验收方式），提交与任务对应
- 重构和新功能分开做

## 禁止事项

- 未做与改动匹配的验证就声称完成，或把未执行的检查说成通过
- 未经确认进行大范围重构
- 写基于关键词匹配的脆弱代码
- **给一个概念造第二个真相源**：多一处定义就多一个会各自演化的真相，日后必然对不上。抄一遍是（前后端共用类型的物理来源是 `packages/shared-types/`，新代码使用 `@sailfish/shared-types`；`shared/types/` 仅兼容转导出），换个词重新发明也是——已有联合类型（`TerminalType` / `ConversationKind` 等）就是分类的真相源，另起平行词汇再写翻译函数，兜底分支会把将来的新成员默默归错档。只有真正的新概念才配新建类型。
