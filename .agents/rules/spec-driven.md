# Spec 驱动开发

模块目录下的 `SPEC.md`（或 `*_SPEC.md`）是模块的首要入口。SPEC 记录的是**用户提出的设计要求**——讨论中确认的功能要求、设计取舍、行为承诺。它不是代码的索引，也不是 AI 的实现笔记。

## 检验标准

**SPEC 里的每一句话，都应该是用户能说出口、能看懂、能验收的话。**

AI 编程中用户只提功能要求，不会要求具体代码实现。因此：

- ✅ 进 SPEC：「重连后必须重绑 I/O 监听，禁止静默装成旧会话还在」「联络会话跨重启要记着上下文」
- ❌ 不进 SPEC：内部类名、函数名、变量名、文件清单和执行流程伪代码。公开 API、配置项、协议字段及错误码若是验收契约，可用精确名称描述语义、兼容性和边界，避免混入内部调用步骤

实现细节是 AI 的自由裁量空间；写进 SPEC 只有两种下场——重构时被迫同步（无谓成本），或悄悄过期说谎。代码结构与调用关系的真相源是代码本身和 CodeGraph，不是文档。

## SPEC 内容（按优先级）

1. **设计目标**（最重要）：要解决的问题、成功标准、关键取舍、明确不做的事——来自与用户的讨论，**不是**从代码反推
2. **行为契约**：对外可见行为、不变量、边界条件——用自然语言描述行为；AI/用户可感知的行为词汇（如工具名）仅在作为行为锚点必要时出现，不作章节主体

**长度不限**——约束管内容性质，不管行数。设计决策多的模块 SPEC 长是正常的，只要每一段都是讨论结论。

## SPEC vs Plan 文档

| | SPEC.md（持久） | Plan 文档（一次性） |
|---|---|---|
| 回答 | 要什么 / 为什么 | 怎么做 |
| 语言 | 用户语言；必要时用公开契约名称 | 实现语言，类名/接口/数据模型随意用 |
| 位置 | 模块目录下 | `docs/plans/YYYY-MM-DD-<主题>-design.md`（文件名与文首都写日期；做完改成 `done-YYYY-MM-DD-…`） |
| 生命周期 | 只在讨论确认新设计决策时更新 | 大改动方案落盘 → 完成时升华取舍进 SPEC，文件名加 `done-` 前缀、文首标明已完成（不删；排序后做完的在前，没做的按日期排在后面） |

Plan 是一次性实现方案的记录处；源码、测试和必要的开发指南也可解释实现。需确认的大改动应先用 Plan 供用户审阅技术方向；它是从设计意图推导出来的，推导物过期就让它过期，历史参考而已。

## 流程

- **讨论对齐后、动手改代码前**：把已确认的设计思路写入对应 SPEC 的「设计目标」；未写入不得开始实现
- **改动前**：先读 SPEC，尤其是「设计目标」——实现不得悄悄违背
- **实现偏离设计时**：先与用户对齐并更新 SPEC，再改代码；禁止只改代码不改目标
- **新增模块**：先有「设计目标」，再写代码；完成后补齐行为契约

## 禁止

- 把内部实现清单写成需求，或把从代码反推的行为冒充用户已确认的设计目标
- 把易变实现细节（函数体步骤、临时命名）写进设计目标
- 讨论里定下的取舍只留在对话里、不落盘
- 「改代码就要同步 SPEC」——SPEC 只在讨论确认新设计决策时更新
