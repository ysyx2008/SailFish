# Spec 管理技能

按需为模块生成 SPEC.md，或审计已有 spec 与代码的一致性。

## 何时使用本技能

- 用户要求"给 XX 写 spec"、"生成 spec"
- 用户要求"审计 spec"、"检查 spec"、"spec 是否过期"
- 新增服务/子系统后需要补 spec

## 生成 SPEC.md

### 步骤

1. **阅读目标模块源码**：了解模块对外提供什么能力、承担什么职责（结构查询用 CodeGraph）。
2. **参考已有 SPEC 模板**：读取 `electron/services/agent/SPEC.md` 了解格式基准（注意其中实现细节内容属历史遗留，新 SPEC 不得模仿）。
3. **撰写 SPEC.md**，包含以下章节（**设计目标优先**）：

```markdown
# <模块名> SPEC

> Last verified: <今天日期>

## 职责
<1-2 句话描述模块做什么>

## 设计目标
<!-- 最重要：来自与用户讨论并确认的思路，不是从代码反推 -->
<!-- 按主题组织，每条含：问题 / 成功标准 / 关键取舍 / 明确不做 -->

## 行为契约
<!-- 对外可见行为、不变量、边界条件，自然语言描述 -->
```

4. **遵循原则**：
   - **核心检验标准：SPEC 里的每一句话，都应该是用户能说出口、能看懂、能验收的话**
   - **区分公开契约与内部实现**：内部类名、函数名、变量名、文件清单和执行伪代码不进 SPEC；公开 API、配置项、协议字段、错误码可用精确名称描述语义、边界及兼容性。具体标准以 `.agents/rules/spec-driven.md` 为准
   - **设计目标 > 契约**；若只有行为描述没有用户确认的设计目标，视为不合格
   - 有用户讨论共识时：先写入「设计目标」再实现；无讨论时：设计目标写「待与用户对齐」，勿用实现细节填充
   - 长度不限——约束管内容性质，不管行数
   - 易变实现细节（函数体步骤、临时命名）不进设计目标
   - 用中文撰写

5. **放置位置**：
   - 子系统目录（如 `agent/`）→ 放在目录下 `SPEC.md`
   - 单文件服务（如 `ai.service.ts`）→ 放在同级目录，命名为 `<SERVICE>_SPEC.md`（如 `AISERVICE_SPEC.md`）

## 审计 SPEC.md

### 步骤

1. **扫描所有 SPEC 文件**：`find electron/services -name '*SPEC.md'`
2. **逐个检查**：是否有实质的「设计目标」（非空、非套话、明显来自讨论结论）；是否混入代码实现内容（类名/方法名/API 表/文件清单/执行流程伪代码）——有则标 ⚠️。公开 API 若作为行为契约出现，要核实实现是否满足承诺；不要求补齐内部 API 清单，结构问题查 CodeGraph
3. **报告结果**：

| Spec 文件 | 状态 | 问题 |
|---|---|---|
| agent/SPEC.md | ⚠️ 需纯化 | 混入大量实现索引（架构图/类清单/执行流程），设计目标被淹没 |
| foo/SPEC.md | ⚠️ 不合格 | 仅有行为描述，无用户确认的设计目标 |
| config.service.ts | ❌ 缺失 | 无 SPEC.md |

4. **修复问题 spec**：实现索引内容可直接删除（纯化）；**设计目标不得凭空编造**——缺失时标 ⚠️ 并询问用户，或标注「待与用户对齐」
5. **不自动生成缺失 spec**：仅报告缺失情况，让用户决定是否生成

## 注意事项

- 生成 spec 后不需要跑测试（spec 是纯文档，不影响代码行为）
- 审计时不要修改源码，只修改 SPEC.md
- 如果模块非常简单（< 100 行、只有 1-2 个函数），可以建议用户跳过，不必每个模块都有 spec
