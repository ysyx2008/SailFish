# 编程技能 SPEC

> Last verified: 2026-09-26（初版做完）
> 总的定位与取舍见 `electron/services/agent/SPEC.md`「编程是默认关着的高级技能」。本文件只写这份技能自己的承诺。

## 设计目标

来自 2026-09-26 讨论确认。

### 要解决的问题

秘书现在也能写简单的软件，但工具不趁手：只能全盘找文件名，搜内容要自己拼命令；一次只能改一处；改坏了没有退路；改完括号没配平、缩进错了也不知道，要等跑起来才发现，有的语言压根没有检查命令，就永远发现不了。

### 成功标准

- **先打开项目**：这场在哪个目录干活由秘书先说清。打开时它就看到项目大概的目录结构、当前 git 分支和改动情况、这是什么语言、检查和测试该用什么命令，以及项目里写好的开发约定（给 AI 看的那些说明文件）。约定太长就截断并说明，不整本灌进去。
- **按内容搜**：在项目里按原文或正则搜，跳过项目忽略的文件（依赖目录、构建产物）；可以只看哪些文件命中、或只看命中数；结果有上限，超了说明。
- **按模式找文件**：比如「所有测试文件」，跳过忽略的文件，最近改过的排前面。
- **一次改多处**：同一个文件里的几处修改要么全改上，要么一处都不改；有一处对不上就整次作废，并说清是哪一处。
- **改完自动查语法**：每次改完文件，如果这次改动新引入了语法错误，结果里直接提示在哪。文件里原本就有的不报；认不出的语言不查；只说「可能有」，不拦这次修改——解析器偶尔会把很新的合法写法认错。认得的语言随安装包带：JavaScript、TypeScript（含 TSX）、Python、Go、Rust、Java、C#、C、C++、PHP、Lua、Shell、YAML、JSON、HTML、CSS。运维常改的脚本和配置（Shell、YAML、JSON）必须在里面——改坏配置往往比改坏代码更要命。
- **能撤回**：每轮开始前自动给项目留一个检查点。说「刚才那轮撤掉」，就能把项目退回那一轮开始前，连它用命令改掉、新建的文件也一起退。退回前先把当前状态也留一个，退回本身也能撤。检查点存在旗鱼自己的数据目录里，**不改项目自己的 git**。
- **检查点不能把磁盘吃掉**：项目本身是 git 仓库时，借读它已经存着的内容，只多存它没有的（没提交的改动、新文件），所以打开项目时那一个几乎不占地方。检查点只留最近 7 天；30 天没打开过的项目，它的检查点整份清掉；项目找不到了（删掉、挪走）且 7 天没用过，也整份清掉——外置盘没插、网络盘断了看起来也像「没了」，不能一找不到就清。单个超过 20MB 的文件不进检查点，撤回不会动它，这一点要说出来。
- **退不回去要说清**：机器上没有 git、项目太大来不及留检查点时，说明这一轮撤不了，不假装能撤。

### 关键取舍

| 选择 | 放弃 | 原因 |
|---|---|---|
| 搜索、读、改、跑命令 | 代码结构索引 / 类浏览器 | 初版像 Claude Code；结构索引重，先用出感觉再说 |
| 语法检查挂在每次修改的结果里 | 单独一个「检查语法」工具 | 模型不会记得每次都去查；改完当场说最管用 |
| 只报新引入的错误 | 报文件里所有错误 | 原有的错误是噪音，会把真正的新问题淹掉 |
| 常用语言直接打进安装包（约 18MB） | 只带几种、其余联网下载 | 安装包已有四百多 MB，十几 MB 无所谓；装上就能查，不看网络脸色 |
| 检查、测试、git 都用现有跑命令 | 专门工具 | 模型本来就会用这些命令；把各家输出硬拆成结构化结果只会是一堆脆弱的文本匹配 |
| 检查点放旗鱼数据目录 | 在项目的 git 里建分支 / 暂存 | 不能动用户自己的仓库 |
| 借读项目 git 里已有的内容 | 完全不碰项目的 git、整份另存 | 整份另存每个项目都要多占一份项目大小（旗鱼仓库实测 74MB），借读后首个检查点不到 1MB、快近十倍；只读不写，承诺从「不碰」改为「不改」 |
| 检查点命令改的文件也能撤 | 只备份秘书用改文件工具动过的文件 | 后者最省地方，但命令改掉、生成的文件撤不回 |
| 退回也要确认 | 退回直接执行 | 退回会覆盖文件，期间用户可能自己也改过 |

### 明确不做

- 类浏览器、结构索引、语言服务
- 改动前后对比的界面；远程项目
- 不替用户决定 git 推送、丢改动该不该问——那是命令审计的事

## 行为契约

- **项目目录管什么**：打开项目后，本机文件的相对路径、后台跑命令的默认目录落在项目根。终端窗格是用户自己的终端，它的目录不替用户改；在窗格里跑检查、测试时由秘书自己先进项目目录，这一点要跟模型说清，不能让它以为命令会自动落在项目里。
- **搜索不出项目**：搜索和找文件只在项目里；指定了项目外的目录直接说明，不悄悄搜到别处。
- **检查点什么时候留**：打开项目时留一个；之后每一轮开始时留一个，不拖慢秘书开口，但这一轮动手改任何东西之前一定已经留好。伙计的活不另留（算在主人那一轮里）。
- **撤回退到哪**：不指定时退到上一次有改动的那一轮开始前。已经被撤回撤掉的内容不再当默认目标，所以连撤几次会一步步往前退，不会把刚撤掉的又恢复；要回到撤回之前，得明确指定那一个。
- **撤回前确认的清单必须是真的**：确认框里列出会改回、会删掉哪些文件。用户同意之前项目又变了（比如确认框开着时他自己改了文件），就按新的清单再问一次，绝不拿旧的同意去删新文件。
- **撤回只动快照里有的**：项目忽略的文件、嵌套的其他仓库、项目自己的 git 数据一律不碰；不会顺着链接删到项目外面。删不掉的文件如实列出；撤到一半失败要说清，并告诉用户怎么回到撤回之前。
- **撤回只有主人能做**：伙计可以用编程的其他工具，不能撤回。
- **借读的内容没了要说清**：用户删了项目的 git 数据、或改写历史并清理掉旧内容，依赖那些内容的检查点就不完整了。退回前先核对，不完整就说这个检查点撤不了，绝不退一半；每次打开项目也整体核对一次，发现借读的来源没了或内容缺了，旧检查点作废、从头再留，并告诉用户之前的撤不了了。一时读不到项目的 git（超时、盘抖了一下）不算「没了」，不许因此作废检查点。缺了一处就整份作废、不挑出完好的留着：项目自己的 git 平时只清两周以上没人用的内容，检查点只留 7 天，撞上的只有用户手动深度清理这种少见情况，不值得为它做逐个检查点的核对。
- **大文件说清楚**：超过 20MB 没进检查点的文件，打开项目、一轮开始新出现时、撤回确认的结果里都要列出来，说明撤回不会动它们。当时太大没进检查点、后来变小了的文件，撤回到那时也不能当成「后来新建的」删掉。
- **很大的文件不查语法**：几百 KB 以上的文件改完不查，免得界面卡顿。
