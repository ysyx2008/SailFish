# 本地联系人（contact）

> 落盘：2026-10-13

## 设计目标

秘书要能**稳定地认人**：听到一个名字或简称，找得出这是谁、在哪个单位、什么角色、邮箱和即时通讯怎么找到他。旧做法是一份让模型自由增改的 Markdown 笔记，用久了会出现同一个人两条、同类信息写法各异、邮箱埋在句子里，模型还会整篇重写。这和当初待办从笔记改成结构化记录是同一个原因。

- **只做「认人」这一层**：每人一条，记姓名、别名/简称、是人还是机构、单位、角色、邮箱 / 电话 / 即时通讯，外加一段自由备注。关系和近况写在备注里，用人话，不拆成字段。
- **同名的人可以有好几个，同一个人不记成两条**：同名很常见，名字一样不等于是同一个人，所以不因为同名拦着不让记。但秘书新增时，姓名或简称与已有的人完全一样，或者邮箱、电话与已有的人一样，先把这几位拿给它看：是同一个人就把新信息补进原来那条，确认是另一个人再新建。只是名字里有同一个字不算一样。用户在联系人页里新增同名的人，提示一下已有谁、可以打开那条，但不拦；改名改成与别人同名也照常保存。
- **写入只走工具**：秘书不能直接改联系人文件；旧笔记也不再在免确认名单里。
- **提到谁带谁**：联系人不进心跳，也不整本带上；它和待办不同，没有截止、没有状态，不需要定时提醒。你在任务或联络里说的话里出现了某个联系人的名字、简称、邮箱或电话，秘书这一轮就会看到这个人记着的信息，像认识他一样接话，不用先去查。记下的简称就是你平时怎么叫这个人，再短也认，只有一个字的不认。同名的几位一起带上，由秘书分辨或问你；名字交叠分不清是谁时（「张伟明」里既有「张伟」也有「伟明」）也都带上，只有整个落在一个更长的名字里才不单算（说「沈义君」不会连带出「义君」）。一句话里提到太多人只带前几位，其余只报名字。同一场对话里已经带过、信息没变的不再重复。只认你说的话：秘书在后台跑的关切和唤醒、派出去的伙计、系统自己递进来的回执和通知都不带。
- **和待办放在同一个地方**：联系人是秘书替用户记着的人，和待办一样从秘书菜单打开，排在待办上面，占主区域，随手能看。在这里可以搜、改、删、新增，秘书记错了用户能发现并纠正。面板上不放合并：秘书新增前会先核对，记重的情况本就少；同名又常是两个人，放一个合并入口只会让人在一长串名字里瞎找。真记重了，跟秘书说一声，由它把信息补进一条、删掉另一条（2026-10-14 用户决定）。
- **入口一样，打扰不一样**：联系人没有截止时间，菜单上不挂计数，也不提醒。
- **对话里看得出是谁**：改、删、查到或列出联系人时，对话里写这个人的姓名；同名或看不出是谁时带上单位、角色，没有就带一个邮箱或电话；改名写成原来到现在。内部编号只留给秘书接着改、删，不出现在对话里。
- **不做**：往来记录、组织架构、分组标签与导入导出、待办那种状态与排序。
- **以后的方向**：即时通讯里「各渠道最近联系的人」、邮件里的地址，日后挂到同一条联系人上，不另存一份。本次不做。

## 旧笔记怎么过来

- 升级时先把旧笔记备份一份，原文件不动。
- 程序不猜 Markdown 格式。由联络问一次要不要整理，用户同意后秘书读原文，逐个记进来；原文里没有的邮箱、电话不补。用户说以后再说，下次启动再问；说不用了，就不再问。
- 待办的迁移还在等用户回话时，联系人这次先不问，免得两件事同时打扰。
- 只有秘书明确记下「迁完了」之后，旧笔记才收进备份。征询期间秘书顺手记了几个新认识的人，不算迁完。
- 迁完之前，查不到的人会提示旧笔记里可能有，秘书可以去翻那份。
