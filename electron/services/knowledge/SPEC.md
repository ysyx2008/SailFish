# Knowledge Service SPEC

> Last verified: 2026-09-16

## 设计目标

### 对用户和 AI 只有一个名字：知识库（2026-10-18）

- **问题**：同一个东西，界面多处叫「知识库」，秘书的工具说明和整理分组叫「档案室」，用户和 AI 看到的是两个名字。
- **成功标准**：
  1. 用户看得到的文字和给 AI 看的提示词、工具说明，一律叫「知识库」，英文叫 Knowledge Base；不再出现「档案室」。
  2. 「记忆」和「知识库」的区别靠记忆栏目里每个标签下的一句说明讲清：记忆是 AI 记住的关于用户和各台主机的事实；知识库是用户放进来的原文，AI 需要时去翻。
- **关键取舍**：选「知识库」是因为行业通用、用户熟悉、改动小；曾考虑「档案室」，因为要改的文字多、用户倾向知识库而放弃。区别靠说明文字，不靠换词。
- **明确不做**：不改钉钉里的「知识库」（那是钉钉的产品名）；不改技能标识、工具名这类内部名字；已写好的历史方案文档不回头改。

### 档案按目录到场，原文才是依据（2026-10-15）

- **问题**：每轮对话自动翻档案时，全库挤在固定的几个正文片段里。无关的东西挤掉该到的，用户只觉得秘书没以前准，账单和报错都看不出来。标题本身又太短，只靠标题会把该想起来的文件漏掉。另一头，秘书还整理不了自己的知识库：放文件要人去设置里上传，而且往往得先把整份文件读进对话。
- **成功标准**：
  1. 每份放进知识库的文件有一个目录位置。自动翻的时候可以限定在某一级目录及其下级；没限定就仍是全库。限定之外的文件不会自动出现，需要时仍能搜、能列出来。范围外的目录名和文件名也不进同一个池子。
  2. 自动带到对话里的，主要是对上的目录、对上的文件（路径、标题，有说明就带一行），另外最多贴两小段特别贴的原文。整段有字数上限。对上的目录只带目录本身，不把里面的文件全部倒进来；文件要自己的标题对上才出现。说明写歪时，靠原文里的字面还能把文件捞回来。目录名和文件名按各自的相似度算，不重做原来的正文索引。
  3. 说明还没写好时，目录和文件名已经能把对上的位置露出来。说明写失败，或者说明那份索引坏了，不影响目录和文件名。目录和文件名这份额外的索引也坏了，才退回正文片段。不能变成什么都想不起来。
  4. 说明在界面上看得见、能改。人改过的，原文换版时不盖掉，并标明它还停在旧版；人确认仍适用后才重新对齐。
  5. 说明在空闲时慢慢补，不占用放入文件的那一下。一次补多少、一天补多少有上限。没指定用哪个较省的模型，就不自动写，免得悄悄用最贵的模型烧额度。静默时段不写。
  6. 秘书可以把本机上的一个文件放进知识库，正文不进入这次对话。可以列目录（只有路径、标题和一行说明）。自己放进去的可以自己删；用户放进去的，删之前要征得同意。删掉之后，按意思找和按字面找都不会再翻到它。没有回收站。清空全库、导入导出、重建索引仍只在设置里。
- **关键取舍**：三级记忆那条检索路一行不动，档案另走一条。树先划定在哪一片里翻，目录名和文件名是这一片里的地图，说明补的是标题表达不了的问法，正文仍只留少数特别贴的片段。目录名和文件名的向量放在已有的向量库里，和正文分开；改一个名字只改这一条，不再整份重写。正文那张表不改，原来的正文不用重新嵌入。说明是导航，不是依据，必须能指回它所基于的那一版原文。先做目录、说明和这条到场方式；章节级索引、废止标记、文件之间的冲突发现，以及和过往对话线索并成一层，这次不做。
- **明确不做**：不改主机记忆和过往对话现在的检索融合；不把说明当成可以引用的条文；不在没指定模型时自动生成说明；不给秘书清空全库、导入导出、重建索引。

### 秘书自己整理知识库的目录（2026-10-15）

- **问题**：知识库是秘书自己的仓库，整理目录却还要人到设置里做。它只能在放进一份文件时顺便写个位置。建一个空目录、把已经在库里的文件挪走、给目录改名、删掉一整个目录，都做不到。
- **成功标准**：
  1. 放进文件、删一份、整理目录，放在一个按需拿出来的技能里。搜索、打开全文、列目录、把这场对话的自动翻阅限定在某个目录，仍是手头一直有的。
  2. 可以建子目录。空目录会留下来，直到被删掉。文件挪走之后，原来的目录也还在，除非把它删掉。
  3. 可以把已经在库里的文件挪到别的目录，可以给目录改名，里面的文件和下级跟着走。目标位置已经有东西时不硬盖。
  4. 删掉一个目录时，里面的文件和下级一起删掉，删掉的文件同样再搜不到。目录里只要还有文件，就先征得同意，并说明有多少份。空目录直接删。删单独一份时，自己放进去的可以直接删，用户放进去的要先问。没有回收站。
- **关键取舍**：放入、删除和整理都不常用，不摊在每一轮的工具里。删掉一整目录的误伤面大，所以只要里面还有文件就问，不看出处。删单独一份仍看出处，因为一次只动一份。没有回收站。
- **明确不做**：不把清空全库、导入导出、重建索引放进这个技能。

### 按字面找仍用原来那一个搜索（2026-10-17）

- **问题**：编号、缩写、专名按意思经常对不上。秘书要能自己选择按正文里出现的字去查，目录名和文件名也要能对上。另开一个工具，它每轮都得在两个搜索之间挑。
- **成功标准**：
  1. 仍是原来那一个搜索。不填时按相关度，和现在一样。选了按字面，才在正文、目录名和文件名里查找出现过的词，不按意思相近来排。
  2. 对上的目录只给出目录本身。文件名对上的，给出路径、标题和文档编号；正文里没有这些词，就不附原文。正文对上的，给出含这些词的片段和文档编号。同一份只出现一次。先是目录，再是文件名，然后是正文片段。
  3. 自动翻到眼前的门槛和找法不变。主机上记下的事、过往对话不进这次字面查找。
- **关键取舍**：字面查找只用已经建好的词索引，不把文件再读一遍，也不跑语义。目录名和文件名不写进正文那份词索引，免得把自动翻阅带偏。
- **明确不做**：不为此新建一个工具；不放宽自动翻阅的门槛；不把目录名和文件名写进正文的词索引。

### 设置里按目录树看档案（2026-10-17）

- **问题**：知识库在设置里是一排胶囊加一张平铺的列表，和旁边的设置对不上，也看不出目录层级。
- **成功标准**：
  1. 记忆和知识库用设置里统一的标签切换，不再自己套一层盒子。
  2. 左边是目录树。根在最上，下级缩进，可以展开、收起。空目录也在树上。点一个目录，旁边只列它直属的文件，再下一层留在树上。
  3. 文件用和输入框附件同一套系统图标。知识库没有原来的磁盘位置，就按文件类型取；系统给不出时，用附件那套备用图标。
- **明确不做**：不把长度、入库、维护从这一页挪走。

### 秘书列目录时要看得见层级（2026-10-18）

- **问题**：秘书列知识库时，把整个子树的文件摊平给它，从不列目录。库里一旦分了层，根下仍是一整页文件；空目录它永远看不见；写了一个根本不存在的目录，得到的话和真有的空目录一样，分不出对错。结果它会下结论说「没有分过类」。
- **成功标准**：
  1. 列一个目录，一次只给这一层：先是直属的下级目录（各写里面一共有多少份文件，含更深的层级），再是直属的文件（路径、标题、一行说明）。要看更深一层，就列那个下级目录。
  2. 空目录也列出来，并说明里面还没有文件。
  3. 写了不存在的目录，要明说没有这个目录，不能当成空目录。
  4. 文件很多时仍有一次最多列多少份的上限，超出的说明还有多少份没列。
  5. 秘书想一次看清整棵目录结构时，可以自己选择把这个目录下所有层级的目录一并列出来（不填就是根）。这时只列目录，每个目录写里面一共多少份文件，不列文件。目录最多列一千个，超出的说明还有多少个没列。不选的时候仍是一次一层。
- **明确不做**：不给秘书新增列目录的工具，仍是原来那一个；列出来的仍不带正文。

### 记忆单独成一个栏目，设置里只留设置项（2026-10-18）

- **问题**：设置里的「记忆与知识库」把两种用法塞在一页：一半是看内容、改内容、整理目录的工作区（目录树、右键、阅读区），一半是字数上限、入库方式、索引维护这些调参。工作区越做越像联系人、待办那样的独立界面，放在设置里既挤又不顺。
- **成功标准**：
  1. 秘书菜单里多一个「记忆」，和联系人、待办一样的打开方式，点开后占主区。
  2. 栏目里记忆和知识库并排，用一对标签切换。记忆：看、改、删个人和各台主机的记忆。知识库：看目录树、右键整理、读文件、改检索说明。
  3. 设置里的这一页只剩设置项：记忆字数上限、检索说明用哪个模型、自动翻阅的范围、入库方式、嵌入设备、重建索引、清空全库。页里不再有管理列表。
  4. 只是换了地方，行为不变：记忆和档案的内容、整理规则、删除前要问的规则，都和现在一样。
  5. 没有知识库设置的版本（简化版）也没有这个栏目。
- **关键取舍**：管理是在里面干活，设置是调参，两样放一页会互相挤占版面。清空全库、重建索引这类一次性的重操作仍放在设置里，不进栏目，免得在日常浏览的地方误点。
- **明确不做**：不改记忆和档案本身的任何行为；不把设置项搬进栏目；不新增别的入口。

### 「关于用户」只有一份：记忆里的「用户」（2026-10-18）

- **问题**：觉醒页里有一份「用户」画像（用户是谁、称呼、职业、沟通偏好），记忆里又有一份关于用户本人的记忆（身份与职责、长期在做的事、偏好与约定）。内容大面积重叠，两份都会在每次对话开头交给 AI，既占篇幅，也会各写各的、对不上。
- **成功标准**：
  1. 觉醒页不再有「用户」这一项；关于用户的一切只在记忆栏目的「用户」里看、改。
  2. 记忆栏目里这一份叫「用户」（不再叫「个人」），排在第一，其后是本机和各台主机。
  3. AI 每次对话开头收到的「关于用户」只有这一份，不再重复；终端页里的对话也带这一份，不再只在助手里才有。
  4. AI 觉醒、被问到「你对我了解多少」或想补充用户信息时，写的就是这一份，上限和更新方式与现在的记忆一致。
  5. 已有的旧用户画像不能丢，也不能硬塞：升级后第一次有可用模型时，在后台让 AI 把旧画像和现有「用户」记忆整合成一份（去重、按主题分段、不超上限），两份原文都留底。整合成功之前，旧画像照常给 AI 看，不出现空档；整合失败或放不下就保持原样，下次启动再试，不静默截断。
- **关键取舍**：保留记忆那一份而不是觉醒那一份，因为记忆是 AI 随对话自动维护的，觉醒的画像要靠人或一次性写入。身份（你是谁）与灵魂（行为准则）仍留在觉醒，那是 AI 自己，不是用户。
- **明确不做**：不改身份、灵魂、心跳；不改记忆的更新规则与字数上限。

### 记忆写不进磁盘，必须让人知道（2026-10-18）

- **问题**：记忆写盘出错（磁盘满、文件被占用）时，原先只在日志里留一句，调用方一律以为成功了：手动编辑点了保存不报错，重启后改动没了；对话后的自动更新也当成已经记住。
- **成功标准**：
  1. 手动保存、删除记忆失败时，界面弹出失败提示，文本框里的内容不丢，仍处于「未保存」状态。
  2. 写不进磁盘时，内存里的记忆保持原样，不出现「当前这次运行里是新的、重启后又变回旧的」。
  3. 对话后的自动更新写盘失败，按「这次更新没做成」处理，和模型请求失败一样留到下次再记，不当成已经记住。
  4. 写盘失败不影响对话本身继续。
- **明确不做**：不为此给用户弹打扰性的通知（自动更新失败只留日志、下次重试）；不改记忆内容的格式与上限。

### 记忆栏目：编辑不覆盖 AI 刚写的、列表看得出内容（2026-10-18）

- **问题**：AI 每轮对话后会自动更新记忆，而记忆栏目打开着时不会自己刷新；用户在旧内容上改完保存是整份覆盖，会把 AI 期间写进去的抹掉。列表里每份只露出原文开头几十个字，常是一串标题符号，认不出是什么。
- **成功标准**：
  1. 没有未保存改动时，栏目里看到的记忆会跟着最新内容走，不必手动刷新；有未保存改动时不替用户换掉正在编辑的文字。
  2. 保存时如果这份记忆在用户打开之后被改过，不静默覆盖：说明情况，让用户选「覆盖」、「放弃我的修改并载入最新」或「再想想」；直接关掉提示等于再想想，用户正在编辑的文字不动。不自动合并两份文本。
  3. 列表每一项能看出这份记忆讲了哪几个主题、有多少字（占上限多少）、最后一次更新是什么时候。
- **明确不做**：不逐条标来源；更新时间只到整份记忆；不做自动合并。

### 设置里直接整理目录（2026-10-18）

- **问题**：知识库左边能看见目录，但建目录、改名、删除都只能让秘书做。人在设置里右键没有菜单，根目录也点不出下一步。
- **成功标准**：
  1. 在目录上右键可以新建子目录、改名、删除。根目录只能新建子目录，不能改名，也不能删除。
  2. 在文件上右键可以删除。把文件挪到别的目录，仍在打开这份文件之后做。
  3. 删目录时，里面还有文件就先说明有多少份，征得同意后连文件和下级一起删，之后再搜不到。空目录直接删。没有回收站。
  4. 目标位置已经有东西时不硬盖。
- **明确不做**：不在设置里另做一套回收站；不把清空全库放进右键。

### 不为长篇资料动自动到场的门槛（2026-10-15）

- **问题**：基线一度量到长篇文档的自动到场率只有十三问里的两问，看着像个要修的大洞。但那批问题是「灾难恢复有什么要求」这种裸问——没有来源、没有场景，换个专业的人来也一样懵。真实场景里用户会问「证监会的管理办法里，灾难恢复有什么要求」。把同样十三件事改成带来源的问法重跑，自动到场从两问变成十问（15.4% → 76.9%），主动搜更是条条第一。所以那个洞是出题方式的伪影，不是产品缺陷。
- **成功标准**：承认提问本身带不带语境，决定了召回该不该发生。问题足够开放时，由它自己决定是上网搜还是翻知识库，这是它该有的判断，不是需要系统代劳的事。
- **关键取舍**：不调那道门槛。门槛对短句记忆是合适的，为长文档放宽会让无关内容挤进每一轮对话，而那个代价只在噪音率和篇幅里看得见。三级记忆是花了很多心血才稳定下来的，不为新功能动它。
- **明确不做**：不写「遇到 X 就去搜知识库」这类行为规则式的提示词（按关键词触发的叮嘱换个说法就失效）；不把知识库正文整份注入上下文；不为了抬高某个指标去改召回参数。
- **基线自身的教训**：问题集的措辞会决定结论。裸问量出来的是「语境缺失」，不是「记忆不行」。日后出题要带上真实场景里会有的来源与限定，两种问法都留着，差值本身就是有用的数字。

### 后台维护不许碰用户刚存进来的东西（2026-10-15）

- **问题**：上一条的基线工具刚接进回归就把一个真 bug 顶了出来——同一份资料、同一批问题，单独跑能想起来四分之三，可库里先放两份无关文档再跑，就一条也想不起来了。查出来跟召回质量无关：知识库会在启动后自己做一次收尾，把「索引里有碎片、清单里却没有对应文档」的残渣清掉（上次异常退出就会留下这种残渣）；而这个收尾一边照着开始时的那份清单认人，一边删东西和整理磁盘，于是把用户此刻正在导入、还没登记进清单的文档当成残渣删了。用户看到的是：文档明明在列表里，搜却永远搜不到。只在恰好有残渣时发生，所以偶发、难复现。
- **成功标准**：不管库里有没有残渣，刚存进去的东西必须立刻搜得到。这里说的「存进去」包括三件事，都走同一套先写索引后登记的顺序，所以都得护住：用户导入的文档、它替某台主机记下的事实、它为对话建的检索条目（后两件是秘书每轮都在做的事，比导入文档更频繁）。残渣该清还是会清，只是不急于这一刻。
- **关键取舍**：写入优先，收尾让路——残渣不占用户看得见的东西，晚点清都来得及；而收尾撞上写入会毁掉用户刚存的资料，这个代价不能接受。让路之后必须真的补做：收尾只在启动时安排一次，让一次就当没有了的话，「下次再清」就是空话（命令行每次导入都正好撞上这一次，于是永远不清）。收尾要清哪些东西在开工时就定下来，期间新出现的一概不碰；动手删之前再确认一次没人在写。
- **明确不做**：不因为这件事给写入加锁排队（写入本身很重，不该为了一次收尾等着）。

### 记忆召回要有一条能对照的基线（2026-10-15）

- **问题**：现在召回好到什么程度，只存在体感里。谁动了门槛、条数、排序，没人能证明是变好还是变差——变差也不会报错，只会悄悄少想起几件该想起的事。实测还暴露了一个体感发现不了的盲区：一份真实的监管法规放进来，自己主动搜能准确搜到对应条文，但平时聊天它几乎从不自己想起来。原因是长篇文档的段落跟口头提问「像得不够」，被门槛挡在外面；而库里多数内容是短句记忆，像得够，所以体感一直是好的。用户想把行业监管规定放进来提升秘书的专业水平，按现状做不到。另外，同一份 PDF 从命令行入库，入进去的是乱码，还报「添加成功」。
- **成功标准**：
  1. 能固定一组文件和一批问题，跑一遍就得到数字：该想起来的想起来了吗（分「我主动搜」和「它自己想起来」两个口径分别给）、不该想起来的有没有乱凑过来、每轮自己想起来的内容占了多少篇幅。
  2. 问题由 AI 读完文件自动出候选，人只做勾选或否决，不用手写。
  3. 跑出来的结果能存档，两次结果能并排对比。
  4. 真实文件可能涉密，文件本身不进代码仓库；仓库里自带一份中性的样例语料和问题，换台机器、没有用户数据也能跑。
  5. 任何格式的文件从命令行入库，和从界面入库得到的内容一致。
- **关键取舍**：指标必须成对给。只看「想起来的比例」，最省事的改法就是把门槛调低——比例一定涨，代价是无关内容开始挤进每一轮对话，而这个代价不在那个数字里。所以同时要量不该来的有没有来、以及每轮占了多少篇幅；只有该来的更多、不该来的没变多、篇幅没失控，才算改好了。
- **明确不做**：这把尺子只量，不顺手改任何召回门槛与排序（量出来的问题另案处理）；不做界面；不替用户定最终问题集，AI 只出候选；不设「不过线就不许发布」的自动闸门，存档与对比由人看。

### 更新记忆时看完整对话，接着对话的缓存（2026-10-11）

- **问题**：每轮结束后更新记忆（个人的、各台主机的都一样），只拿到用户这一轮的原话和截短的过程——每个工具的参数、结果各剩几百字，回复只剩前五百字——再另起一次请求交给模型判断。一是看不全：同一场里前面聊过的、工具原文里的细节都看不到；二是拿不到缓存：这次请求和对话本身从第一个字就不一样，每次全价；三是每次都把整份记忆附进去，判断要改时又整篇重写输出，最贵的输出花在原样抄写上，重写时还会把没打算改的地方写坏——现有记忆里已经出现断成半句的话。
- **成功标准**：
  1. 更新记忆接在刚跑完的那场对话后面问：看到的是完整对话和工具原文，不截断。这次请求和平时长得一样（工具清单照带），只在说明里讲这一步只更新记忆、不执行操作，前缀一字不差，能吃到缓存。模型没写记忆、转头去调工具，就再要一次并禁止调用——那一次拿不到缓存也要把结果拿到。
  2. 一轮要更新几份（个人、各台主机），一次问完，各份分别给出结果。
  3. 记忆本来就在对话开头的，不再附一遍；这场对话开始以后被改过的、或者开头没带上的那几份，在末尾补上最新版本。模型拿来比对的永远是最新的记忆。
  4. 只交变化：没有新东西就说没有；有变化只交改了的那几段，没涉及的原样留着，不整篇重写。
  5. 不必每轮都问：自上次更新以来新增的内容攒够一定量再问，量按模型返回的真实用量算，不靠估。上下文交接之前必须问一次——交接以后原文就不在了。一轮跑完、一阵没人接着说话时也问一次，免得最后几轮没攒够量就漏掉；这一次要赶在缓存还有效的时候发。
  6. 能写哪几份仍按原来的规则定：只聊天只写个人，真正动过手的那台才写那台。模型只能往给定的那几份里写；事实归哪一份由它看完整对话判断，拿不准就不写——宁可少记，不要记错。
- **关键取舍**：重复送进去的前缀是最便宜的部分。原样重送按缓存价计；为了少送而裁掉前面，前缀一变缓存全丢，剩下的全价，反而更贵。真正省钱的是不重附记忆、不整篇重写、不每轮都问。不标「上次记到这里」：避免重复记靠比对最新记忆的内容，跟上次记到对话哪个位置无关；标位置还得在交接后跟着换算，白添一件要维护的事。
- **明确不做**：这次不做每天集中整理（跨多场对话归纳规律、让近期动态按时淡出、整份统一口吻）——先看这一步的效果再定；不改唤醒、关切在记忆上的现有规则；不改记忆怎么注入对话、每份多长；关软件时不为补这一次拖着不退出。

### 原生加速库加载失败时，语义搜索仍要能用（2026-09-16）

- **问题**：部分 Windows（尤其 Server、没有独立显卡）上，本地语义搜索整条挂掉。原生加速库在加载阶段就失败，后面的「加速不行再改用 CPU」走不到，知识库搜索也跟着废。
- **成功标准**：原生加速库加载失败时，语义搜索仍能用，只是会慢一些。仍在独立进程里跑，不回到主进程。按文件名搜、按关键词搜不受影响。没有可用显卡时，自动和「仅 CPU」都要能把知识库开起来，用 CPU 做向量化。加速那一步如果把进程打退出去、卡住，或者加载完却算不出结果，也算失败，接着改用 CPU，不能让整库起不来。
- **关键取舍**：宁可慢，也不能整条搜索陪葬。不靠猜错误文案来分类，而是先试加载原生库，失败再用一套不依赖系统显卡的实现。
- **明确不做**：不往安装目录塞系统 DLL；失败后不把推理拉回主进程；不为这种机器单独再打一份安装包。

- **明确不做**：不在记忆页再放「存到别处」「从文件夹恢复」；不因此关掉本机自动留份。

### 清空知识库必须打出指定文字（2026-08-29）

- **成功标准**：这个动作的按钮一看就是危险操作。确认时必须亲手打出指定那几个字，打错或取消都不删。

### 记忆每份多长，可以自己定（2026-08-29）

- **问题**：每份记忆现在固定五千字。有人觉得太短记不住，有人觉得太长、占每次对话太多。
- **成功标准**：设置里的记忆页可以改每份记忆的字数上限。默认仍是五千。能设的范围大约一千到两万。改完对之后的自动更新和手动保存生效。字数统计跟着新上限走。
- **关键取舍**：已有记忆不因为改小了就立刻裁掉。下次秘书更新、或你自己保存时再生效。
- **明确不做**：不按不同主机设不同上限；不因此改知识库文档（你上传的那些）的长度。

### 删对话时，对应的检索条目一起去掉（2026-08-27）

- **问题**：对话删了之后，知识库里还留着这条对话的检索摘要。之后再搜「上次那件事」，仍可能翻到已经不存在的对话。
- **成功标准**：删一条对话时，知识库里对得上这条对话的检索条目一并去掉。删完再按这件事去搜，不该再命中它。
- **关键取舍**：只删对得上号的。对不上的旧条目先留着，不为此扫整库。
- **明确不做**：不补扫、不清已经对不上号的旧条目；不删对话过程中记下的长期事实（对你、对某台机器的认识）；不因此重建知识库。

- **成功标准**：记忆与知识库设置不再展示该入口；即使用户以前选过某台 MCP，搜索也只走本地知识库。
- **明确不做**：本次不实现外部 MCP 知识库。

### utilityProcess 隔离 + 桌面端禁止静默回退主进程（2026-07-23）

- **问题**：Embedding / LanceDB 设计进 utilityProcess；打包 `asarUnpack` 缺传递依赖时 worker ESM 失败，旧逻辑 `warn` 后回退主进程——功能「看似能用」，Windows 上堵 UI，测试也发现不了。
- **成功标准**：
  - worker 所需依赖必须在 `asarUnpack` 物理目录，ESM `import()` / `require` 可解析。清单至少覆盖：`onnxruntime-common`、`onnxruntime-web`（及其运行时依赖）、`apache-arrow`、`@huggingface/jinja`、`@huggingface/tokenizers`、以及 `transformers→sharp` 的 `detect-libc` / `@img/colour` / `semver`、`lancedb` 的 `reflect-metadata`、`apache-arrow` 的 `tslib` / `flatbuffers`。unpacked 包无法再解析仍在 asar 内的依赖。

  - **唯一例外**：CLI / shim 下 `utilityProcess.fork` 不可用时走进程内模式（无 UI、也无 worker 可选）——这不是「失败后降级」。
- **明确不做**：不在 worker 失败后再偷偷 in-process「救活」；不靠关键词解析错误串做分类。

### 向量库 worker 掉了要能自愈，不能静默变空（2026-08-16）

- **问题**：向量库 worker 崩溃或被系统回收后，应用仍认为自己「已初始化完成」，之后所有读写都落到没有数据库连接的进程内分支上——写操作报错、检索返回空。用户看到的是「记忆突然什么都搜不到了」，没有任何提示，只能重启应用才恢复。
- **成功标准**：
  - worker 掉了以后，下一次读写会自动把它重新拉起来并恢复正常，用户不必重启应用。
  - 重新拉起失败时明确报错：不能悄悄返回空结果冒充「没搜到」，也不能偷偷改用主进程加载向量库（这是既有约束，此处一并守住）。
  - 多路操作同时发现 worker 不在时只重建一次，且重建不留下孤儿进程。
  - 清空知识库不需要先把 worker 拉回来——用户来清库往往正是因为库坏了、起不来。
- **明确不做**：不做后台定时探活（按需重建足够）；不因一次重建失败就永久停用向量库——用户可能只是一时资源不足。

### worker 重启不得留下孤儿进程（2026-08-16）

- **问题**：11.6.0 用户现场一天内嵌入 worker 被拉起 89 次、只退出 6 次——83 个 worker 还活着却已无人管理，每个占 100–250MB，整个应用的进程组内存冲到 16GB，最终主进程内存耗尽崩溃。多路记忆召回并发触发重启时会互相打断：上一代 worker 的死亡通知把新一代的初始化握手判成失败，于是「重启失败 → 再重启」越滚越多（当天 45 次重启失败、101 次请求被中断），而定期重启本身只发生 6 次，并非主因。
- **成功标准**：
  - 任一时刻只有一个在用的嵌入 worker；被替换掉的 worker 必须真正退出，不允许出现「活着但没人管、也杀不掉」的进程。
  - 上一代 worker 的退出或被杀，不得影响新一代 worker 的初始化握手和它正在处理的请求。
  - 多路召回同时要求重启时共享同一次重启，不各自拉起进程、不互相杀死对方刚建好的 worker。
  - 重启过程中不得让调用方误以为「本机不在 worker 模式」而走到没有加载模型的进程内推理上。
  - 长时间运行（跨天、多轮定期重启）后进程数与内存回到基线，不随运行时长单调增长。
- **明确不做**：不用「进程数超限就杀最老的」这类兜底来掩盖泄漏；不因此取消定期重启——它是抑制推理内存池膨胀的必要手段。

### 确证救不回来之后，必须自己把向量侧重建出来（2026-08-23）

- **问题**：向量库缺了一个数据文件，三份备份里都没有它，保留的损坏现场里也没有，回退到出事前的版本同样不可行（中间那些版本早被压实清掉了）。于是每次启动都是同一套动作：看到损坏标记 → 挨个试备份 → 都读不开 → 保留坏表 → 检索继续失败 → 再标一次损坏。库就这么废了大半天，用户全程不知情，只有翻日志才看得见。既有决定「救不回来也不清库重建」保住了数据，代价是不给任何出路——数据是没丢，但功能一直是坏的。
- **成功标准**：
  - 恢复手段全部试过、并且能确证救不回来之后，自动把向量侧重建出来，不要停在坏状态里等人发现
  - 重建出来的成果不许被下一次启动的恢复流程当成坏库盖掉，否则就是换了个花样的每次启动都重烧
  - 只重建向量这一半：关键词索引和源文档是另一套数据，不受影响，也不重新解析
  - 重建过程和结果用户都看得见，不能闷头跑几个小时
  - 重建失败不再重来，不能变成每次启动都重烧几小时的循环
- **关键取舍**：
  - 这一条**收窄**了下面 08-19 与 08-22 两条「不要因此全量重建」，不是推翻。那两条禁的是「一发现损坏就反射性推倒」——那时候好备份往往还在，重建反而把本可恢复的数据毁掉。这里说的是完全相反的处境：所有恢复手段都已试过，且能证明缺的东西哪儿都不存在。分界线是**有没有确证救不回来**，不是「要不要重建」。
  - 敢做成自动的前提是代价可控：走到这一步的损坏在真实用户那里罕见（已查明的成因是两个实例共用同一份数据目录，一个进程压实时删掉的数据文件，另一个进程手里的清单还指着——正常用户只开一个实例，撞不上），而重建只重算向量、不重新解析文档，本机实测十几二十分钟。若哪天重建的代价变回「几小时」级别，这条自动就该重新讨论。
- **明确不做**：
  - 备份还没试完、或结论尚未确证时不重建；不碰关键词索引与源文档；一次重建失败不反复重来。
  - **不把「一份备份都没有」当成确证救不回来**。看起来这批人最没退路、最该自愈，但「读不开」并不等于「坏了」——另一个实例正握着这张表时它同样读不开，而表是完好的。挨个试过备份才是能证伪的证据；没有备份可试时我们手里什么都没有，猜错就毁掉用户唯一的副本。这种情况留给用户手动发起强制重建：由人决定丢弃，不由程序猜。

### 修复索引不得把「读不出来」当成「里面是空的」（2026-08-23）

- **问题**：向量表坏到枚举不出内容时，查询会返回空集合。启动时的补建路径知道这件事，会先确认表里究竟还有没有数据，避免把「全库都缺」当真；用户手动点的「修复索引」却没有这道确认，会把九千多篇全判成缺失，然后往那张已经坏掉的表里重新 embed 几个小时——修不好，纯白烧。
- **成功标准**：「读不出来」和「真的是空的」必须区分开；分不清时宁可拒绝并说明原因，也不能按「全都缺」开工。
- **明确不做**：不靠错误文案猜是哪一种情况。

### 救不回来的时候，别把磁盘吃掉（2026-08-22）

- **问题**：知识库坏了以后，每次启动都会把手上的备份从新到旧挨个试一遍。每试一份，就把当前这份整个改名留下来当"现场"，一份两三百兆。用户有三份备份，于是每启动一次就多留三份、七百兆，且从来没人清。开发调试期间频繁重启，三天堆出一百四十多份，数据目录被撑到 55 G（其中 42 G 全是这些现场）。而这三份里只有第一份是真的——后两份是刚从备份复制进去、又被判定读不开的副本，内容和备份本身一模一样。更浪费的是"这批备份都救不回来"这个结论已经是确定的，却每次启动都要用几百兆的复制重新验证一遍。
- **成功标准**：
  - 一次启动最多留下一份现场，且是用户数据真正坏掉的那个样子；同一轮里试更早备份时被换下来的副本不留
  - 现场有数量上限，超出的自动清掉最旧的——占用不随重启次数增长
  - 同一批备份试过一遍都救不回来，下次启动不再重来，直到备份有更新或用户手动发起恢复
  - 现场集中放在一处，用户一眼能看出它占了多少、能整个清掉
- **关键取舍**：现场是留给排查的，不是存档。真要排查，最近一份就够用，更早的那些内容雷同；宁可少留，也不能让"将来也许用得上"把用户磁盘吃光。
- **明确不做**：不因为救不回来就清库重建（守住上一条已定的约束）；不自动删用户的备份。

### 坏了不要把坏的存成最新备份，更不要整库推倒（2026-08-19）

- **问题**：检索发现向量文件缺了一块，会标成损坏。下次启动本应先回到上一份好备份，只补缺的几篇。实际却先把当前这份坏的存成最新备份，再按它恢复；读不开就把整张向量表丢掉，九千多篇从头建。好备份被轮替掉后，热重载会连着全量重建。
- **成功标准**：
  - 已经标了损坏时，这次启动不再自动备份
  - 恢复后如果还是读不开，从新到旧试更早的备份；都读不开也不要整表丢掉，也不要因此全量重建
  - 自动备份只在没有损坏标记时做（启动时磁盘还没被这次进程打开，复制是安全的）
- **明确不做**：这次不改「检索时怎么判断文件缺了」；不在退出时做同步备份（会拖慢关掉窗口）。

### 初始化失败熔断（2026-07-27）

- **问题**：11.4.1 禁止回退后，Agent 每次 L2/L3 召回仍会 `initialize()`；打包缺依赖时反复 fork Embedding worker，日志上千条「退出 code=0」，拖垮资源并放大「未响应 / 终端黑屏」。
- **成功标准**：
  - Embedding / Knowledge 任一侧初始化一旦完整失败，**闩锁**该错误：后续 `initialize` / `search` / `embed` 直接抛出同一错误，**不再 spawn worker**。
  - 用户显式换设备（`setDevice`）、`dispose` / 备份恢复后再允许重试——不是靠解析错误文案分类。
- **明确不做**：不按错误字符串猜「可恢复 / 不可恢复」；不做分钟级自动重试风暴。

## 职责

本地知识库引擎。提供文档向量化、混合检索（向量+BM25）、文档分块、嵌入模型管理、主机记忆、对话索引、加密导入导出。Agent 通过它实现"跨会话事实记忆"（L2）和"对话经验召回"（L3）。

## 关键行为 / 数据流

**文档添加 → 可搜索**：
1. `addDocument(doc)` → `Chunker.chunk(content, strategy)` → `DocumentChunk[]`
2. → `EmbeddingService.embedChunks(chunks)` → 向量数组
3. → `Storage.addVectors(docId, chunks, vectors)` + `BM25.addDocument`
4. 文档元数据写入 `documents.json` 索引

**搜索（混合检索）**：
1. `search(query)` → 向量搜索 top-K + BM25 搜索 top-K 并行
2. → `Reranker.fusion()` 合并 → 去重 → 返回 SearchResult[]

**主机记忆（智能合并）**：
1. `addHostMemorySmart(hostId, memory)` → 先 `searchHostMemories` 找相似项
2. → 命中阈值则合并/覆盖，否则新增（行为见 `memory-utils.ts`）

**对话索引（异步）**：
1. Agent `finalizeRun` 完成后异步调用 `indexConversation`
2. → 提取 user task + final answer → 嵌入 → 入向量库（独立表）

## 关键约束

- **必须 `initialize()` 后才能搜索**——未就绪时 `search` 直接返回空数组
- **大文档必须分块**——`Chunker.chunk` 按 `chunkStrategy` 分段
- **嵌入模型下载不阻塞启动**——后台下载，`ModelManager` 通过 EventEmitter 报告进度
- **加密统一走 `crypto.ts`**——不得在其它模块内联实现
- **导入导出方法叫 `importData` / `exportData`**——不是 `importKnowledge` / `exportKnowledge`
- **MCP 通过 `setMcpService` 延迟注入**——不能放进构造参数（循环依赖）
- **主机记忆相关方法名都带 `HostMemory`**（如 `searchHostMemories`、`getHostMemoriesForPrompt`），不是 `getHostMemory` / `deleteHostMemory`
- **`data_corrupted` 仅重建向量侧**——BM25 为独立 JSON，损坏时保留 BM25，启动增量补向量即可
- **已标损坏时禁止自动备份**——避免把坏库存成最新备份、把好的轮替掉。自动备份仍在启动开头、向量库尚未打开时做（磁盘是上次退出状态，复制安全），受 30 分钟间隔限制，保留最近 3 份
- **打开失败不得清表**——缺文件、读不开时保留现有向量表，不得整表丢掉；只有换了嵌入模型、维度对不上才清旧向量
- **恢复从新到旧试备份**——启动发现损坏标记时先恢复；读得开才算成功。最新这份读不开就试更早的；都读不开则跳过启动补建，不要把「枚举失败」当成「库是空的」去全量重建
- **损坏现场集中存放并限量**——现场统一放在 `knowledge-broken/`，只留最近 2 份；同一轮里试更早备份时换下来的副本不留档（前提是确认它确实是副本，前面的恢复没做成时换下来的仍是用户原始数据，必须留）；老版本散落在数据目录根下的现场启动时收编进来一并轮转
- **一批备份试遍都读不开就记下结论**——下次启动跳过恢复，不再用几百兆的复制重新验证注定的结果；备份有增删更新、或用户手动发起恢复时该结论作废
- **恢复后增量补差集**——读得开的备份换回去之后，只补和当前文档清单的差集，不全量重做向量
- **孤儿 chunk 后台清理**——`initialize()` 后 `setImmediate` 定向删 chunk；残留 &lt; 50 跳过整表重建
- **退出时 `disposeAsync`**——主进程 `cleanupAllServices` / SIGINT·SIGTERM 会 compact LanceDB 并停 worker
- **嵌入推理**——有显卡时才走加速；没有可用显卡时自动用 CPU。「仅 CPU」不试显卡。加速失败、进程退出、卡住或算不出结果时，改用 CPU，知识库仍要能启动；原生库本身起不来时，改用不依赖系统显卡的实现，仍在独立进程里跑。设置里可以选自动或仅 CPU。
