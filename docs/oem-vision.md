# OEM 说明（开源主线如何被快速 OEM）

> 状态：产品方向说明（2026-07-13 从工作台 Monorepo 方案中拆出）  
> 读者：想了解「开源 vs OEM、如何换皮换岗」的人；不要求先读工程细节  
> 说明：岗位工作台是 OEM 的主要扩展手段之一；工作台抽包工程见 [`workbench-monorepo-design.md`](./workbench-monorepo-design.md)

---

## 一句话

**开源主线提供一套旗鱼 Agent 底座与可扩展工作台架构；企业各自 Fork 做 OEM（我们自己也会有一份）。**  
岗位差异收在工作台，不重造智能体；企业系统开放 Skill 或 MCP 即可被 AI 驱动。

---

## 组织约束（为什么必须标准化）

目标用户侧常见现实：**很小的科技团队（约十人量级）要支撑几千人、多业务线的公司做 AI 赋能**——例如国有企业内部信息化团队。

在这种约束下，若「每个业务场景各自建一个智能体、各自建一套系统、再持续运维」，人力与成本都不可持续。因此产品必须是：

- **一套标准化底座**反复复用（Agent、记忆、终端、身份、下发与治理）  
- **按岗位叠加工作台**（界面 + Skill + MCP + 岗位设定），而不是按场景重造系统  
- **业务系统只开放 Skill / MCP** 即可接入，IT 架构保持简单  

工程上一切取舍（不抽 Agent 进业务包、工作台只声明能力、能力开关与协议进开源配置/公共模块）都应服从：**小团队 × 大组织，只能靠标准化产品摊薄成本。**

外采常需招投标（立项采购可达数月），难以敏捷响应业务；自研则风险自担，需靠窄切口、人审与扩展点纪律把控质量。AI 编程降低了小团队打造中台的门槛，但放大不了错误方向——方向必须是标准化底座 + 岗位工作台。

## 心智模型

| 概念 | 含义 |
|---|---|
| **智能体（Agent）** | 公司统一的秘书底座：思考循环、记忆、终端、工具调度都在这。默认同一套，可按岗位配置开关。 |
| **工作台** | **一个岗位一个工作台**（金融分析、运维值班、人事助理……）。含界面 + 岗位技能 + MCP + 人设/行为设定。 |
| **多团队** | 不同研发团队支撑不同业务部门，各自交付工作台，互不阻塞核心发版。 |
| **开源主线** | 本仓库持续发布的社区/产品主干：通用能力 + 可被快速 OEM 的扩展架构。 |
| **OEM Fork** | 企业各自 Fork 开源主线做自己的企业版（我们自己也会有一份）；接 OA、加岗位工作台、连内部系统。不是第三条「内部专用」产品线。 |

---

## 工作台可定制的 Agent 能力（产品契约）

业务团队通过「工作台描述」覆盖默认智能体，而不是 fork 一套 Agent。清单可随演进加项，但**定制面挂在工作台上**，不散落进核心类内部。

| 能力面 | 说明 | 开源主线现状（摘要） |
|---|---|---|
| 界面 / 布局 | 岗位专属 UI，或声明式区域组合 | descriptor：`renderer` / `regions`（工程方案推进中） |
| 人设与行为 | 岗位 system prompt 片段 | descriptor：`agentPrompt` |
| 专用技能（Skill） | 本岗位会哪些技能 | descriptor：`skills`（声明；desktop 装配） |
| 专用 MCP | 本岗位连哪些企业系统工具 | descriptor：`mcpServers`（声明；desktop 装配） |
| 记忆开关 | 是否启用工作记忆 / 长期知识注入等 | ⏳ 目标已纳入；字段待策略层设计 |
| 召回 / 检索 | 是否启用情景记忆检索等 | ⏳ 同上 |
| 执行松紧 / 工具范围 | 确认策略、可用工具子集等 | ⏳ 同上 |
| 模型与密钥 | 开源版本地配；OEM 可由服务端下发 | ⏳ 属 OEM 控制面 |

字段与装配细节见 [`workbench-monorepo-design.md`](./workbench-monorepo-design.md)。

## 开源主线与 OEM Fork（两版本）

产品线只有两条，**不要**再拆「内部版」第三条代码线：

| | **开源主线（本仓库）** | **OEM Fork（每家企业一份）** |
|---|---|---|
| 谁维护 | 主线持续发版 | 各企业自己维护自己的 Fork |
| 我们自己 | 维护开源架构与发版 | **也会有一份 OEM Fork**，作为第一家落地样本 |
| 其他企业 | 用开源或跟主线 | 愿意 OEM 就 **Fork 一份**，自己接 OA、做岗位与对接 |
| 放什么 | Agent 底座、工作台扩展点、通用工作台、个人向能力 | SSO / 身份、岗位工作台、对内 Skill·MCP、下发与治理、计费审计等 |
| 和主线关系 | 上游真相源 | 跟上游合并；定制走扩展点，少改核心文件 |

**开源架构的职责**：让「Fork 之后快速做 OEM」成为默认路径——**换皮走品牌配置、换能力集走 features、换岗走工作台、接系统走 Skill/MCP**；**不强迫每家企业改 Agent 内核**。

**OEM 侧典型体验**（各 Fork 自行实现完整度）：

1. 改品牌配置即可换软件名 / 展示标识（见下节）  
2. 对接企业 OA / SSO（OAuth 2.0 / OIDC）→ 员工用公司账号登录  
3. 按岗位下发或装配：工作台、Skill、MCP、模型与密钥  
4. 服务端控制面（可选但企业常用）：计费、成本、审计、岗位管理、技能中心、MCP 中心  
5. 客户端按岗工作；业务系统只开放 Skill 或 MCP 即可接入 AI  

岗位工作台如何在开源主线里被清晰交付（Monorepo / SDK），见工程方案；各 OEM 的身份与控制面在各自 Fork 中演进。

### 跟上游合并（降低 Fork 分叉风险）

原则写在开源说明里，供各 OEM 参照；**各 Fork 自己的跟版节奏 / CI 写在各自仓库**，不塞进开源主线运维细节。

- OEM **优先只加 / 只改**：自有 `shared/oem.config.ts`（由模板生成，勿改上游模板冒充配置）、工作台包、Skill/MCP、配置、身份与下发模块  
- OEM **避免改**：Agent 主循环、Conversation 聚合根、核心 IPC 契约（除非回馈开源主线）  
- 岗位与策略差异一律挂在工作台描述 / 策略下发上，不复制一套智能体  
- 勤合、小合；冲突时优先把补丁改成扩展，而不是长期分叉核心文件

## 品牌 OEM：有 OEM 信息则以 OEM 为准

原则：**软件名称、展示用标识等，只要配置了 OEM 信息，一律以 OEM 为准**，优先于开源默认「旗鱼 / SailFish」。尽量 **改配置、换资源**，不要改业务底层代码。

**跟上游更新零冲突（2026-10-15 验收标准）：** OEM 仓库直接合入上游时，这些个性化内容不产生冲突。

做得到的前提只有一条：厂商长期保留的改动，都放在上游仓库里不存在的文件上。上游永不提交这些文件，两边就不会改到同一处。

| 文件 | 上游有没有 | 厂商仓库 |
|---|---|---|
| 配置模板与开源默认 | 有，上游维护 | 厂商不改 |
| 厂商自己的配置 | 没有（忽略，不提交） | 强制纳入本仓库 |
| 厂商自己的图标 | 没有 | 只在本仓库新增 |

厂商若再改上游也在改的文件（业务代码、打包配置、主线图标），冲突会回来。新增的岗位工作台是新目录，不改上游已有文件，则同样不冲突。

更新地址、关于页和帮助里的链接、安装身份、图标已经改成只读这份配置。厂商要换的，写在上游不提交的配置和自己的图标目录里；开源默认与原来的旗鱼一致。

| 项 | 现状 | 说明 |
|---|---|---|
| 配置入口 | ✅ 模板 + 本地 `oem.config.ts`（`src/config/oem.config.ts` re-export） | 名称、logo、版权、版本、`features` |
| 应用内展示 | ✅ 已接入 | `shared/brand.ts` 等读 `oemConfig` |
| 打包名 / 应用 ID / 数据目录 / 协议 / 命令行名字 | ✅ 已从同一份配置读取 | 见下文「分发、链接与安装身份」；开源默认与原来一致 |
| 安装包 / 系统图标等 | ✅ 已由配置指定厂商自己的图 | 不改主线那几份图标文件；不写就仍用旗鱼的图 |

**桌面侧「快速 OEM」是否差不多：**

- **换皮** + **换能力集**（觉醒/终端等可关）+ **换岗**（工作台）齐了 → 主干支撑基本成形。  
- **完整企业中台**（SSO、按岗下发、计费审计等）仍在 OEM Fork / 控制面轨道。

安装名、应用 ID、图标与更新地址、对外链接一并从同一份 OEM 配置读取（打包时也读这份配置，避免安装包仍是旗鱼）。图标不替换主线文件，配置指向厂商自己另放的图。

## 能力开关：开源默认可配，OEM 按需裁剪

开源主线带有**私人秘书**属性（觉醒、心跳、联络、关切等）；OEM 面向岗位/企业场景时，**不一定需要秘书全套**。原则：

- **能关的用配置关**，不要 fork 后删代码或注释入口  
- **开源默认尽量全开**（高度可配置，而不是写死「必须有觉醒」）  
- **OEM 改 `shared/oem.config.ts` 的 `features`（及同类开关）** 即可裁出自己的产品形态  

与「换皮 / 换岗」并列，这是 OEM 的第三块：**换能力集**。

### 建议纳入配置的能力面（产品清单，非已实现字段）

| 能力面 | 开源默认（倾向） | OEM 为何要关 |
|---|---|---|
| **觉醒**（个性 / 心跳 / 主动行为、觉醒面板等） | 开 | 企业岗位助手未必要「活人秘书」叙事与自循环 |
| **联络**（`companion` 常驻关系线） | 开 | 纯任务/岗位工作台场景可能只要任务会话 |
| **关切 / Watch** | 开 | 部分 OEM 只要对话 + 工具，不要委托监控 |
| **羁绊气质 / 俏皮文案**（`bond`：placeholder 分池、任务完成趣味 footer、里程碑 toast、首 token 彩蛋与调侃、prompt 羁绊段） | 开 | 企业岗位助手要正式语气，不要私人秘书彩蛋 |
| **本地终端工作台** | 开 | 纯助手 / 纯业务台、不允许本机 Shell 的场景 |
| **SSH 终端工作台** | 开 | 无运维诉求、或安全策略禁止远程终端 |
| **独立助手工作台**（含产出物等） | 开 | 仅终端向 OEM 可能不需要 |
| **赞助 / 社区入口等** | 开（已有 `showSponsor`） | 企业版通常关闭 |

说明：

- 工作台是否可用，与「觉醒等产品能力」可以分开配：例如保留助手工作台，但关掉觉醒心跳。  
- Steam 与 OEM `features` **必须**收敛到统一判定（工程方案中的 `isWorkbenchAvailable`），禁止两套 if。  
- **不必**把每个小按钮都做成开关；优先配整块能力 / 整类工作台。细粒度走工作台 descriptor。

## 身份与 SSO（开源有协议，默认关闭）

| 问题 | 结论 |
|---|---|
| 现在有没有强制账户 / 单点登录？ | **开源默认没有**。单机可用；不挡未登录用户。 |
| OAuth 2.0 / OIDC 协议代码放哪？ | **进开源主线公共模块**（与邮箱/飞书「连外部服务」的 OAuth 分开）。OEM 不应各自造协议轮子。 |
| 开源默认开不开 SSO？ | **`features.sso` 默认 false**。打开并配置 IdP 后才走应用登录。 |
| 「兼容协议 = 任意企业 SSO 开箱？」 | 标准 OIDC 对接会很快；仍需配 Issuer/Client/回调；厂商私有扩展长尾另适配。 |
| 完整组织/RBAC/计费？ | **控制面后置**；开源先交付协议 + 最小会话（如 `AuthUser`），不假装一夜做成企业中台。 |

**节奏**：协议底座与工作台/features 可并行落在开源；控制面下发在 OEM Fork / 后续专题。

## 分发、链接与安装身份（2026-10-15）

厂商合上游时，只改自己那份 OEM 配置和自己的图标，不再改业务代码或打包文件去换地址、换安装身份。缺的字段用旗鱼的开源默认，旧配置不用改也能跑。

**开源默认必须与今天完全一致**（旗鱼、SailFish、现有应用 ID、数据目录名 SailFish、协议名、命令行名字 sailfish）。已经装过旗鱼的用户不受影响。厂商只在自己的配置里改；改了安装身份就等于另一款软件，不会自动把旗鱼的旧数据迁过去。

### 不写和写成空

两项不是一回事。

- **不写**（旧配置里没有这项）：用旗鱼今天的默认。已经在用的配置不用改也能跑。
- **写成空**：这项关掉，不退回旗鱼。关于页和帮助菜单里不显示这一项，避免关掉之后还留着旗鱼的入口。

### 分发

两处更新地址：代码仓库，以及国内或企业自己的更新根地址。更新说明、语音包的具体链接由这两项拼出来，不各写一遍。

两处都可以写成空。只空一处，就只用还写着的那一处。两处都写成空，这个版本不做应用内更新，由企业自己分发，不退回去连旗鱼的仓库；语音包也不再从网上拉。

### 对外链接

官网、文档、问题反馈、交流群号、联系邮箱、协议链接、技能清单地址。

联系邮箱现在写死在关于页，要能换成厂商自己的。协议链接开源默认指向现在的开源协议；企业版写成自己的协议地址，或写成空让这一项不出现。

技能清单是旗鱼自己的技能列表。写成空就只用内置技能，不连旗鱼的站点。不必把每条技能网址写进配置。

社区技能市场是旁边那个公开市场，单独一个开关，默认开着。企业版关掉即可，不再配一个地址。这是一项好测的小开关，不属于本轮暂缓的大块能力开关。

### 安装身份（同一台电脑上两家产品不能抢同一个）

| 项 | 开源默认（保持现状） | 说明 |
|---|---|---|
| 应用 ID | 现有值 | 系统用来区分是哪一家的安装 |
| 安装名 | SailFish | 安装包、程序文件名；界面上的中文名仍用品牌名 |
| 数据目录名 | SailFish | 用户数据放在哪一家名下；自定义数据位置的指针也用这个名字。选定后不要再改，否则用户数据会找不回 |
| 唤起协议名 | sailfish | 别的软件用链接打开本应用 |
| 命令行名字 | sailfish | 终端里敲的命令 |

Windows 开始菜单和桌面快捷方式的显示名跟随品牌里的中文名，不另设一项。

浏览器助手不按厂商拆。扩展要上架商店，各做一份不划算；浏览器也只允许一个固定名字连到桌面程序。各 OEM 共用现在这一份助手（商店列表、扩展身份、连接名字都不进配置）。同一台电脑装了两款时，先启动的那款占住连接，后启动的不能抢；先开的退出或已经不在了，连接才空出来。

**图标由配置指定，不替换主线文件（2026-10-15）。** 直接改仓库里的图标，合上游时会和主线的图标冲突。厂商把图放在自己的目录里（主线没有这些文件），配置里写上用哪一张。不写就用旗鱼现有的图。

只指定一张彩色应用图标。窗口、关于页、安装包、各平台的图标格式都从这一张生成，不必在配置里逐个列出。菜单栏图标是另一张黑白轮廓，可选；不写就仍用旗鱼的菜单栏图标。

**不放进配置：** 应用内预览用的内部地址（用户看不到）；数据目录里面的文件名（目录已经按厂商分开，就不会串）。第三方接口（模型厂商、钉钉、飞书、微信等）也不是厂商自己的服务器，保持不动。赞助入口已有开关，收款码换图片即可。Mac / Windows 的签名证书和密码也不进这份配置：它们是密钥，放在厂商自己的构建环境里，不写进会提交的文件。现在没有证书就继续不签名，不必为以后预留配置项。

**能力开关本轮不扩、不验收（2026-10-15）。** 觉醒、联络、关切、终端、羁绊这类开关要证明「关掉之后没有漏入口」，影响面太大，现在测不全。字段和现有行为保持不动，开源默认仍全开，不在这一轮承诺关干净。SSO 的开关留下：它默认关，只守登录这一条，开或关都好测。
