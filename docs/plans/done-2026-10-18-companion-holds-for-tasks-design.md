# 联络派完任务后，这一轮等着任务回来（方案）

状态：已完成（2026-10-18 编码、测试、代码审查、真模型端到端通过；桌面界面与微信真机留给用户验收）

设计取舍已写入 `electron/services/agent/SPEC.md`「联络任务管理」→「派完任务，这一轮等着任务回来」。本文只写怎么做。
取代 `2026-10-18-receipt-reply-follows-last-line-design.md`（已放弃，原因见下）。

## 起因

联络派的任务做完，回执交给联络。联络派完任务那一轮就收工了，回执回来时只能另起一轮；另起的一轮被设计成「关起门」（整轮折成一行，只有 `talk_to_user` 发的话露出来）。真实记录（22:43 / 22:44）里联络两次都把结果写成了完整回复，没调 `talk_to_user`，话被折叠，用户看着像任务卡住了。

## 为什么换方向

上一版是给「这一轮已经收工」这个前提打补丁：要新写一套按渠道指定发送（IM 服务、投递管道都要动），并且「最近联系过的渠道」不等于用户现在在哪。

命令的做法绕开了这个前提：`exec` 转后台、答应了要接着盯，这一轮就不收工（`BackgroundWatch` + `runUntilIdle` 的「挂着等」），用户说话让路、结果到了在同一轮里接着说，渠道由这一轮自己的回调决定。任务回执本来就是返回事件，`deliverTaskReceipt` 对「这一轮还开着」已经有现成的送进去的路径（排进 `pendingUserMessages`、叫醒挂着的这一轮）。缺的只是：联络派完任务后，没有任何东西让这一轮挂着。

和派伙计（子 Agent）、盯后台命令是同一件事：这一轮只要还有欠着结果的活就不收工，结果一到就在这一轮里接着说。差别只有两点：活的生命周期归谁（伙计随这一轮、命令归这场对话、任务是独立的一场对话，可能比这一轮活得久，所以要兜底）；按停停不停（伙计、命令一起停，任务不停）。

## 做法

**把「派出去的任务」登记成联络这场对话的一份后台工作**，复用命令那套挂着等的机制，不新造。

1. **记账**（`task-supervisor.ts`）：联络开头的运行（新建；再交代让已停的接着做；再交代补进联络开头的那一轮）登记「还欠联络回执」；完成/失败/被停的回执交付给联络之后销账。要用户确认、提问不销账（任务还没完）。补进用户开头那一轮的再交代不登记（那一轮不会有回执）。兜底销账：超过等待上限；或过了开跑宽限（30 秒）后任务实例已不在跑、也没有待发的结束事件。
2. **等待的实现**（新增 `tools/task-watch.ts`，实现已有的 `BackgroundWatch`）：
   - `isPending` = 还欠回执；
   - `holdStarted/holdEnded`：和命令一样，挂起时在联络那一轮里放一张「等待任务『标题』」的卡并走秒，结束时收口；
   - `checkpoint` 返回空：不为看进度叫醒模型；
   - `stop`（用户按停联络）：只释放等待，**不停任务**；
   - `release`：收卡片。
3. **登记**（`tools/task-manager.ts`）：`create` / `instruct` 成功后，经执行器已有的 `trackBackgroundWatch` 登记；同一场任务只登记一份（再交代时复用并换绑到当前执行器）。
4. **回执文案按处境分两种**：回执正文由 supervisor 组装，附「用户在场」「用户不在这一轮里」两段尾巴（`TaskReceiptText`）；`Agent.deliverTaskReceipt` 按走的是哪条路选一段——送进还开着的这一轮用在场尾巴，另起一轮（含被收回重发的）用不在场尾巴。`agent.ts` 里不出现工具名。
5. **工具描述**（`packages/workbench-companion/src/agent-tools.ts`）：`create` / `instruct` 里关于回执的那句改成新行为。
6. **文案与提示词**（`agent/i18n.ts` zh/en）：见下。**提示词需用户审核**。
7. **命令行**（`electron/cli/index.ts`，2026-10-18 用户确认放进本次）：`--task-wait` 直接当这一轮等的上限（默认 600 秒，0 = 不等）；挂着期间 CLI 并发读标准输入，一行就是一句插话，经同一个说话入口送进联络这一轮；联络问确认时暂停读输入，免得抢键盘。联络开始等时才启动超时，到点按停联络（任务不停）；退出前列出仍在跑的任务。

界面（折叠、分组）不改：联络那一轮是用户开口的一轮，回执作为步骤出现在这一轮里，联络的回复是这一轮的正文，本来就露出来。

## 提示词（最终版，已发给用户审）

回执尾巴（`receipt.footer_present` / `receipt.footer_away`）：

- 在场（这一轮还开着，回执是插进来的）：你这一轮还开着，用户在对话里，你写的话他看得到；不写正文就不打扰他。用户的答复用 manage_tasks confirm 或 instruct 转给那场。
- 不在（闲下来之后被回执叫醒另起的一轮）：这是你闲下来之后被回执叫醒的一轮，用户不在这一轮里；只有 talk_to_user 发的话他才看得到。用户的答复用 manage_tasks confirm 或 instruct 转给那场。

派出任务后的工具返回（`taskmgr.await_hold` / `taskmgr.await_none`）：

- 等着：这一轮在它交回执之前不会结束：你写完要对用户说的话就行，不必自己再等；回执到了会送进这一轮，用户说话也照常收得到。
- 不等（等不住时）：这一轮不会等它；回执到了会另起一轮叫你，那一轮用户看不到。

等待卡片（`taskmgr.await.*`）：「等待任务『标题』· 已等 N」；用户先说话时收成「先回答你，任务还在做」；有回音时「任务有回音了」；按停时「不再等这个任务（任务本身还在做）」。

`manage_tasks` 描述里 `create`：

> 由你开头的这一轮，做完、失败、被停、要用户确认、向用户提问，都会以回执交给你，用户不会直接收到。派出之后你这一轮会等它们回来，最长 1 小时：不影响你继续回复用户、接收新消息，回执到了送进这一轮；用户按停你这一轮只是不再等，任务照常做。这一轮等不住时（重启、被停止、超时），回执到了才另起一轮叫你，那一轮用户看不到。

`instruct` 一条：由你再交代而接着做的这一轮，回执同样交给你，你这一轮也同样会等；任务正在跑时这句是补进那一轮，回执和等待仍跟着那一轮原来由谁开头（用户开头的那一轮不欠你回执）。

## 要注意

- **等的时候联络这条线算「在忙」**：微信新消息走「插话」分支，回「已收到」，由联络在这一轮里答复；`/status`、新对话之类特殊命令在忙时不生效（现在忙时就是这样，等的时间变长后更容易碰上）。是否把特殊命令挪到「忙」判断之前，另议，不在本次范围。
- **插话的答复回到这一轮开头的渠道**：桌面开头、用户中途在微信说话，答复回桌面。命令也一样。已写进 SPEC 的「已知代价」。
- **挂着的这一轮里，联络的「安排了」微信会当场收到**（IM 每定稿一句话就发，不等收工），已读 `im.service` 确认；之后每一句回复同理。
- **兜底仍在**：重启、按停、超 1 小时后的回执仍走「另起一轮、关起门」。
- **按停语义**：`stopAll` 会对每份等待调 `stop`；任务那份不停任务。按停后再来的回执照送（回执本来就豁免「按停不再送后台结果」）。
- **`final_result` 要等挂着的这一轮收工才出现**，期间界面按「进行中」显示；与命令一致。

## 代码审查结论（2026-10-18）

采纳并已修：
- **命令行没有 TTY 时没有保活句柄**：等回执期间所有定时器都不占事件循环，进程可能先于回执退出（TTY 下常驻的读键盘碰巧占着，所以之前的验证没发现）。命令行到点按停的定时器改成占着事件循环；用 `< /dev/null` 真跑一遍，回执在同一轮里读到、进程干净退出。
- **欠账被清掉却没人叫醒等待的那一轮**（开跑失败、回执没投出去）：会守着一张空等的卡到下一个检查点（3 分钟）。清账时新增叫醒联络；有一条测试专门盖这个，去掉叫醒它就失败。
- **确认提问和常驻读键盘同时读同一个标准输入**：双份回显、确认期间敲的字被吞。改成确认前真把读键盘关掉、答完再接上；用 pty 实测 y/N 只进提问、之后的插话照常进联络。

没改（已评估）：
- 工具描述写「最长 1 小时」，命令行默认只等 10 分钟：命令行的上限是用户自己给的参数，联络向用户转述时多半不会精确到时长，不为此在工具描述里写命令行。
- `--task-wait 0` 时返回「回执到了会另起一轮叫你」而命令行随即退出：属测试用法，不为它改提示词。
