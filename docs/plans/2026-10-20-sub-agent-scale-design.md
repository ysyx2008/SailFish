# 伙计大批量并发：不设数量上限，派出即开工

> 状态：**未完成**（2026-10-20 落盘，等用户确认后动手）
> **范围（2026-10-20 用户定）**：先议过「这一期不做缓冲池」，改成伙计更有耐心＋错开起步兜底；讨论后发现兜不住（伙计一直重试会占着额度，挤得用户自己当面的请求失败；一批同时重试也不会收敛），**结论：这一期做缓冲池**，按 §3.2 收敛后的小版本做。伙计限流时更有耐心（§3.1b）仍保留，因为缓冲池按并发调、不数字数，每分钟字数超限仍会出现。错开起步不要了，缓冲池自己会把第一波请求排开。
> 设计目标已写入 `electron/services/agent/SPEC.md`「伙计可以大批量同时干活」。
> 分支：`feat/sub-agent-scale`。想法本：「支持大规模并发子智能体」。

## 1. 要解决什么

一次最多派 10 个、同时开工默认 5 个最多 10 个，多的排队。目标：派多少由秘书定（保险丝 200 个没做完的），派出即全部开工，同时真正向模型发请求的有几个由系统按接口承受力自动调节（§3.2），写法上支持「一份模板加一批条目」，大批量回来的结果不撑满主人的对话。

## 3. 设计

### 3.1 去掉数量限制，加保险丝

- 删掉「一次最多 10 个」和 `max_concurrent`（参数不再出现在工具说明里；旧调用若还带，忽略）。
- 保险丝：花名册里 `pending + running` 的伙计数 + 本次新派数 > 200 → 整次退回，错误里写清当前有多少没做完、上限是多少。常量放花名册模块，一处定义。
- `spawn` 不再按数量排队，`startQueued` 删除：全部立刻 `startChild`。要不要等位由 3.2 的缓冲池决定，发在每一次模型请求上，不在「伙计开不开工」上。仍失败的伙计如实报失败，主人能看到并重派。

### 3.1b 伙计被限流时更有耐心

伙计是后台干活，没人当面等，慢一点比失败好。缓冲池只按并发调节、不数字数，每分钟字数超限仍会有，这是第二层兜底。

- `ChatStreamOptions` 新增 `rateLimitMaxRetries`；`ai.service.ts` 里 429 重试次数由它决定，不传仍是现在的 5。只改 429，不碰网络错误和 5xx 的重试。
- 建伙计时由 Agent 传 20：按「单次封顶 60 秒」算，约 15–20 分钟才放弃，足够跨过好几个一分钟的限流窗口。账户欠费、密钥无效这类等也没用的，仍按原来的判断立刻报错，不重试。
- 等待期间界面沿用现有的重试等待卡：第几次、还要等几秒；伙计行上能看到「限流，等待重试」。
- 与缓冲池的关系：撞 429 要等重试时先放掉名额，重试前重新排队（见 3.2 接入方式），所以耐心等待的请求不会一直占着名额。
- 刻意不做：不让你当面的请求也这么有耐心；不改 5xx / 529 的重试；不单独对 `Retry-After` 做处理。

### 3.2 模型请求缓冲池（`ModelRequestBuffer`，新文件；用户称它「自适应缓冲池」，不是固定数字的闸门）

> 2026-10-20 先议过暂缓、用伙计耐心＋错开起步兜底，后来判断兜不住：伙计耐心重试会一直占着额度，用户自己当面的请求（只有 5 次重试）会被挤得失败；一批伙计同时重试也不会收敛。所以做，但保持下面这个小版本。它按并发和限流反馈调节，不数每分钟字数；每分钟字数的精确节奏仍是想法本里「模型每分钟用量超限时，别只甩一句报错」那条。

位置：`electron/services/ai/model-request-buffer.ts`，进程内单例，`ai.service.ts` 调用。目标是把它做小：一个计数、一条队、两条调节规则（放多少、何时放）。

**为什么放在请求层而不是「同时几个伙计活着」**：伙计大部分时间在等本机工具（网页、命令、远程机器），不占模型接口。若按「活着的伙计数」限，一个要等长工具的批量任务会被白白压低。限的应该是**同时在途的模型请求数**。

**管所有发往模型的请求，不只伙计**（2026-10-20 与用户确认）：额度按账号 + 模型算，不按谁在调用算。仓库里发往模型的 HTTP 只在 `ai.service.ts` 一处，一道缓冲池覆盖全部调用方（对话、取标题、知识重排与整理、记忆压缩、命令行、压测）。TTS、语音、本地嵌入是别的服务，不在里面。

**留下的四件事**：

1. **按分组计数**：键 = 接口地址 + 密钥 + 模型（只在内存里拼，不落盘不进日志）。每组有一个「在途数」和一个「窗口」，在途数到了窗口，后来的排队。
2. **用户当面等的请求不排队**：直接放行，只占一个在途名额、也参与「被限流」的判断。不传标记的调用方一律按这一档（默认值是故意的：新调用方忘了标，也不会被排到伙计后面）。**由此，缓冲池即使有 bug 也最多让伙计和后台变慢，不会卡住用户自己的对话。**
3. **排队的只分两档**：已经开工的伙计接着发的请求排在前面，其余（伙计第一次请求、关切、唤醒、整理）排在后面；同档先到先得。目的只有一个：一批伙计陆续交卷，不是齐头并进最后一起交。
4. **自动调节：有两条，都由报错的情况决定**（2026-10-20 用户提出：这不是一个固定数字的闸门，是按报错情况决定放不放下一个的缓冲池）：
   - **放多少（窗口）**：起步窗口 8。没被限流过之前，每成功一个窗口 +1（等于每一轮翻倍，很快爬上去）；被限流过之后，每成功一整个窗口才 +1。被限流时窗口减半，最小 1。
   - **何时放（缓一缓）**：被限流（429 或 529 过载）后，这一组先暂停放行排队里的请求。暂停多久：接口给了 `Retry-After` 就用它；没给就从 3 秒起，连续被限流每次翻倍，封顶 60 秒；只要有一个请求成功，就归零。暂停结束后窗口已经减半，只放少量出去试探；成功再慢慢放开，又被限流就再缓、缓得更久。当面请求不受暂停影响。
   - 为什么两条都要：每分钟用量这类限制，一旦撞上，接下来这一分钟剩下的时间里发什么都会被拒；只收窗口、仍然立刻放下一个，会一路撞到分钟翻页。先缓一缓才对。
   - 同一批请求同时撞上只算一次：每次调整就换一个「代」，只认在这一代里放行的请求撞上的限流，免得一批 429 把窗口减到 1、暂停翻到封顶。
   - 窗口没有固定上限，实际在途数受需求自然限住。起步窗口、暂停起步值、增长节奏用模拟压测定，不凭感觉。

**刻意不做**（想简单，这些先不上）：

- 不做四五档优先级；不区分关切和伙计谁先。
- 故障转移换了模型档，名额仍记在原来的键上，不换键。
- 不做超时回收名额的看门狗：放名额幂等、每条退出路径都有单测，不靠兜底。
- 不预测限流、不做每分钟字数平滑（那条想法单独留着）。

**接入方式：三处收口，不碰重试**：

- 一个请求从进入方法到最终交出结果，同一时刻最多占一个名额。**放名额是幂等的**（请求持有一个许可，放过就清空，重复放无副作用），所以不怕「某条退出路径忘了放或放了两次」。
- **撞 429 要等重试时，先放掉名额，重试前重新排队**：否则伙计耐心重试时一直占着名额，窗口缩小后又没人管得住重试的那一波。网络错误、5xx、视觉降级、换模型这些重试仍占着名额不放，不改它们的逻辑。
- 三处各加「入口取名额、出口放名额」：`chatWithToolsStream` 和 `chatStream` 在各自已有的收尾函数里放；`chat` / `chatWithTools` 在共用的请求包装外面套一层。撞 429 的那几行各加两句：「告诉缓冲池被限流了」「放掉名额」，重试前（发请求之前）再排队取名额。
- 排队中点停止：从队里拿掉，立刻按已中止收尾。
- 等位期间对调用方的通知：新增 `onBufferWait(waiting: boolean)`，沿用重试等待卡的展示通道，伙计行上显示「等模型空位」。
- 标记由调用方传：`ChatStreamOptions` 新增 `bufferPriority`（`urgent` / `continuing` / `queued`）。Agent 构造伙计时设 `queued`，伙计发过一次请求之后设 `continuing`；关切、唤醒、整理类设 `queued`。

### 3.3 一次派出的两种写法

`dispatch_agents` 参数调整：

- `tasks[]`：老写法，每个伙计一份 `description` + `prompt`（保持兼容），带多少对话仍默认全带。
- `batch`：`{ instruction, items[], fork_turns? }`。每个 item：`{ name?, description, input }`；实际交给伙计的 prompt = `instruction` + 换行 + 本条目的 `input`。不做占位符替换，纯拼接，没有模板语法要教。
- `batch` 的 `fork_turns` **默认不带对话**：一批同类条目互相独立，共同指令本身要写够；不带能把每个伙计开局的字数从整段对话降到一份指令。需要时秘书可以显式指定带多少。
- 两个至少给一个，可同次混用，合计进保险丝。
- 说明书只写事实：两种写法各自是什么、同时开几个由系统按接口情况调节、排队的会在轮到时开工、每个伙计各自占用对话上下文和费用。不写「该怎么选」。

### 3.4 大批量回执

- **长结果落成文件，对话里只留一小段加位置**（2026-10-20 用户提议）：已有的落盘路径本来就是这个做法——结果超出门槛就写进这场的中转目录，对话里只留「共多少字、存在哪、尾部一段」，主人用 `read_file` 取。这次改的只是门槛：直接带回的字数上限不再固定 8000，而是随这场一共派了多少人收紧——人少时和现在一样（8000），人多时降到约 1000；各自上限乘人数保持在一个固定预算内（初值约 40000 字，曲线实现时定）。无状态，不用记「已经送进了多少」，也不会出现「前几位有全文、后几位只有要点」的不公平。
- **总览文件**：每个批次一份，每位伙计一行：名字、状态、结果字数、结果文件位置；伙计一做完就更新。主人要汇总几十个结果时先读总览，再决定读哪几个，或者用命令批量处理（筛选、拼接、统计），不必把全文读进对话。
- **合并敲门**：同一时间窗口（初值 1.5 秒）内做完的合成一次敲门，一条消息里列出多位。主人只被唤醒一次。
- 要核实：`injectSubAgentKnock` 在主人正在跑 / 空闲 / 在 `wait_agents` 里时各是怎么落的，合并要不要改 `waitForNews` 的领取语义（现在一次领一位）。

### 3.5 进度刷新

- 花名册的 `onProgress` 改成合并推送（最多约 4 次/秒），推「变更」而不是整份：新增 `ChildSnapshot` 的 diff 事件，或界面按 id 局部更新。实现前先看 `AgentStep.subAgents` 在界面是整替还是按项合并。
- 主进程不做大对象反复 `structuredClone`：伙计数大时只推有变化的几位。

### 3.6 界面

- 伙计折叠行：「N 个伙计：x 做完 / y 在干 / z 等模型 / w 失败」；点开按状态分组，只渲染可见部分（200 项用虚拟列表或分页）。
- 排队中的不再显示「还没开工」，改显示「等模型空位」。
- i18n：`zh-CN` 与 `en-US` 同步新增文案。

## 4. 不做

- 不加设置项让用户配并发数。
- 不做花费估算和确认。
- 不改伙计不能再派伙计、不能自己找人确认这些现有约束。
- 不做每分钟字数（TPM）的精确节奏控制：缓冲池只按并发和 429 调节；每分钟用量超限那条想法仍单独留着。

## 7. 待核实（动手前先看，不预设答案）

1. 本机命令并发：200 个伙计同时 `exec`，有没有进程级的节流？没有的话，要不要在这次一并做，还是单列一条。
2. `全带` 开局时每个伙计拿到的是父对话的拷贝还是引用，200 个的内存占用。
3. 敲门落到主人的几种状态（见 3.4）。
4. 界面对 `subAgents` 的更新是整替还是按项合并（见 3.5）。
5. 缓冲池放开后窗口可能很大，`ai.service.ts` 里每个 HTTP 连接池的监听数警告（现在设的是 30）会不会刷屏，要不要调。
6. 各家接口被限流的表现不同：有的 429，有的变慢，有的直接断连。上线后看日志里「Rate limited (429)」和超时的次数，作为第二期的依据。
7. 用假的限流接口压一次：200 个伙计在抢额度时，你自己当面的请求不排队、会不会仍因为接口真饱和而失败；若会，要不要让当面的请求也多几次 429 重试。
