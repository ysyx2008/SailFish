# 伙计大批量并发：不设数量上限，同时开几个由系统调节

> 状态：**未完成**（2026-10-20 落盘，等用户确认后动手）
> 设计目标已写入 `electron/services/agent/SPEC.md`「伙计可以大批量同时干活」。
> 分支：`feat/sub-agent-scale`。想法本：「支持大规模并发子智能体」。

## 1. 要解决什么

一次最多派 10 个、同时开工默认 5 个最多 10 个，多的排队。目标：派多少由秘书定（保险丝 200 个没做完的），同时开几个由系统按模型接口的承受力自动调，写法上支持「一份模板加一批条目」。

## 2. 现状（代码里的事实）

| 位置 | 事实 |
|---|---|
| `tools/sub-agent.ts` `dispatchSubAgents` | `rawTasks.length > 10` 直接拒；`max_concurrent` 夹在 1–10，默认 5 |
| `sub-agent-roster.ts` `spawn` | 再夹一次 1–10；`startNext` 按「running 数 < 上限」逐个开工；`startQueued` 只留最后一次 spawn 的闭包（所以后一批改了上限，前面排队的也跟着用新的） |
| `tools.ts` `dispatch_agents` | 说明里写「1-10 个」「默认 5，范围 1-10」 |
| `ai.service.ts` | 没有任何进程级的请求闸门。`chatWithToolsStream` 里 429 最多重试 5 次，指数退避或 `Retry-After`；重试等待期间不占也不让出任何东西 |
| `sub-agent-roster.ts` `recordStep` / `runExisting` | 每个伙计每一步都 `onProgress(this.list())`：每次整份花名册拷贝一遍（含每人全部步骤）再推给界面，是 O(伙计数 × 步骤数) 的重复推送 |
| `tools/sub-agent.ts` `formatKnock` | 每个伙计做完敲一次门，正文带完整结果（超过 8000 字才落盘取摘要）；200 个 = 最多 160 万字进主人对话，且主人可能被敲 200 次 |
| 本机命令并发 | 没查到进程级的上限，待核实（见 §7） |

## 3. 设计

### 3.1 去掉数量限制，加保险丝

- 删掉「一次最多 10 个」和 `max_concurrent`（参数不再出现在工具说明里；旧调用若还带，忽略）。
- 保险丝：花名册里 `pending + running` 的伙计数 + 本次新派数 > 200 → 整次退回，错误里写清当前有多少没做完、上限是多少。常量放花名册模块，一处定义。
- `spawn` 不再按数量排队：全部立刻 `startChild`。排队改由 3.2 的闸门承担。`startQueued` 删除。

### 3.2 模型请求闸门（`ModelRequestGate`，新文件）

位置：`electron/services/ai/model-request-gate.ts`，进程内单例，`ai.service.ts` 调用。

**为什么放在请求层而不是「同时几个伙计活着」**：伙计大部分时间在等本机工具（网页、命令、远程机器），不占模型接口。若按「活着的伙计数」限，一个要等长工具的批量任务会被白白压低。限的应该是**同时在途的模型请求数**。

- 分组键：接口地址 + 密钥指纹 + 模型。限流通常按这个粒度。
- 接口：`acquire(key, priority, signal): Promise<Permit>`；`permit.release(outcome)`；`outcome` 为 `ok | throttled(retryAfterMs?) | error`。
- **持有范围**：一次 HTTP 尝试，从发出到响应结束（流式到流结束）。进入自动重试等待时先放掉，重新发之前再 `acquire`（否则 429 退避期间还占着位）。点停止时排队中的 `acquire` 立刻 reject。
- **自动调节（AIMD）**：
  - 起步窗口 4，慢启动：连续成功一整个窗口就翻倍，到第一次被限流为止。
  - 被限流（429，或 529 过载）：窗口减半，最小 1；一段冷却时间内不再重复减。`Retry-After` 存在则整组暂停放行到那一刻。
  - 之后加性增长：窗口个请求都成功就 +1。
  - 窗口没有固定上限，实际在途数受需求（伙计数）自然限住。参数用模拟压测定，不凭感觉。
- **闸门管所有发往模型的请求，不只伙计**（2026-10-20 与用户确认）：模型接口的额度按账号 + 模型算，不按谁在调用算；伙计只是最大的来源。仓库里发往模型的 HTTP 只在 `ai.service.ts` 一处（别处没有 `chat/completions` 或 `v1/messages`），所以一道闸门就覆盖全部调用方：任务和联络的对话、取标题、知识库重排与整理、记忆压缩、命令行、压测。TTS、语音、本地嵌入是别的服务，不在这道闸门里。
- **优先级**（数字越小越先）：0 用户当面等的请求（任务、联络的对话，取标题、知识重排这类就在回复路径上的）；1 关切、唤醒、后台整理；2 已开工伙计的后续请求；3 伙计的第一次请求。同级先到先得。
- **0 级不排队**：直接放行，只占一个名额、也参与「被限流」的判断。这样一大批在途的伙计请求（流式一条可能几十秒）不会让用户的话等位；若接口真的饱和，用户的请求撞 429 走原来的重试，同时窗口会降下来让伙计让路。1–3 级才排队，窗口缩小时已在途的不打断，只是不放新的。
- 调用方传优先级：`ChatStreamOptions` 新增 `gatePriority`。Agent 在构造伙计时设 2/3（第一次请求由 Agent 自己判断，没发过请求就是 3），关切、唤醒、整理类设 1；不传的一律按 0。**默认 0 是故意的**：新加的调用方即使忘了标，也不会被无声地排在伙计后面。
- 故障转移换了模型档，分组键变了：放掉旧键的名额，按新键重新 `acquire`。
- 等位期间对调用方的通知：新增 `onGateWait(waiting: boolean)`，沿用重试等待卡的展示通道，伙计行上显示「等模型空位」。
- 覆盖的入口：先只接 `chatWithToolsStream`（Agent 主路径，伙计和主人都走它）；其余入口（`chat` / `chatStream` / `chatWithTools`）一并接，因为同一个账号的额度是共用的，漏一个就是一个旁路。接入点放在各自发请求之前，不改它们的重试逻辑，只在重试等待前后放位 / 取位。

### 3.3 一次派出的两种写法

`dispatch_agents` 参数调整：

- `tasks[]`：老写法，每个伙计一份 `description` + `prompt`（保持兼容）。
- `batch`：`{ instruction, items[], fork_turns? }`。每个 item：`{ name?, description, input }`；实际交给伙计的 prompt = `instruction` + 换行 + 本条目的 `input`。不做占位符替换，纯拼接，没有模板语法要教。
- 两个至少给一个，可同次混用，合计进保险丝。
- 说明书只写事实：两种写法各自是什么、同时开几个由系统按接口情况调节、排队的会在轮到时开工、每个伙计各自占用对话上下文和费用。不写「该怎么选」。

### 3.4 大批量回执

- **长结果落成文件，对话里只留一小段加位置**（2026-10-20 用户提议）：已有的落盘路径本来就是这个做法——结果超出门槛就写进这场的中转目录，对话里只留「共多少字、存在哪、尾部一段」，主人用 `read_file` 取。这次改的只是门槛：直接带回的字数上限不再固定 8000，而是随这场一共派了多少人收紧——人少时和现在一样（8000），人多时降到约 1000；各自上限乘人数保持在一个固定预算内（初值约 40000 字，曲线实现时定）。无状态，不用记「已经送进了多少」，也不会出现「前几位有全文、后几位只有要点」的不公平。
- **总览文件**：每个批次一份，每位伙计一行：名字、状态、结果字数、结果文件位置；伙计一做完就更新。主人要汇总几十个结果时先读总览，再决定读哪几个，或者用命令批量处理（筛选、拼接、统计），不必把全文读进对话。
- **合并敲门**：同一时间窗口（初值 1.5 秒）内做完的合成一次敲门，一条消息里列出多位。主人只被唤醒一次。
- 要核实：`injectSubAgentKnock` 在主人正在跑 / 空闲 / 在 `wait_agents` 里时各是怎么落的，合并要不要改 `waitForNews` 的领取语义（现在一次领一位）。

### 3.5 进度刷新

- 花名册的 `onProgress` 改成合并推送（最多约 4 次/秒），推「变更」而不是整份：新增 `ChildSnapshot` 的 diff 事件，或界面按 id 局部更新。实现前先看 `AgentStep.subAgents` 在界面是整替还是按项合并。
- 主进程不做大对象反复 `structuredClone`：伙计数大时只推有变化的几位。

### 3.6 界面

- 伙计折叠行：「N 个伙计：x 做完 / y 在干 / z 等模型 / w 失败」；点开按状态分组，只渲染可见部分（200 项用虚拟列表或分页）。
- 排队中的不再显示「还没开工」，改显示「等模型空位」。
- i18n：`zh-CN` 与 `en-US` 同步新增文案。

## 4. 不做

- 不加设置项让用户配并发数。
- 不做花费估算和确认。
- 不改伙计不能再派伙计、不能自己找人确认这些现有约束。
- 不碰 TPM（每分钟字数）平滑：闸门只按并发和 429 调节；每分钟用量超限那条想法仍单独留着。

## 7. 待核实（动手前先看，不预设答案）

1. 本机命令并发：200 个伙计同时 `exec`，有没有进程级的节流？没有的话，要不要在这次一并做，还是单列一条。
2. `全带` 开局时每个伙计拿到的是父对话的拷贝还是引用，200 个的内存占用。
3. 敲门落到主人的几种状态（见 3.4）。
4. 界面对 `subAgents` 的更新是整替还是按项合并（见 3.5）。
5. 各家接口的并发限制表现不同：有的是 429，有的是慢、有的直接断连。闸门是否也要把「连续超时」当成降窗信号，用真接口试一遍再定。
