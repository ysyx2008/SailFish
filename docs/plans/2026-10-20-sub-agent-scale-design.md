# 伙计大批量并发：不设数量上限，派出即开工

> 状态：**未完成**（2026-10-20 落盘，等用户确认后动手）
> **范围（2026-10-20 用户定）**：先议过「这一期不做缓冲池」，改成伙计更有耐心＋错开起步兜底；讨论后发现兜不住（伙计一直重试会占着额度，挤得用户自己当面的请求失败；一批同时重试也不会收敛），**结论：这一期做缓冲池**，按 §3.2 收敛后的小版本做。伙计限流时更有耐心（§3.1b）仍保留，因为缓冲池按并发调、不数字数，每分钟字数超限仍会出现。错开起步不要了，缓冲池自己会把第一波请求排开。
> 设计目标已写入 `electron/services/agent/SPEC.md`「伙计可以大批量同时干活」。
> 分支：`feat/sub-agent-scale`。想法本：「支持大规模并发子智能体」。

## 1. 要解决什么

一次最多派 10 个、同时开工默认 5 个最多 10 个，多的排队。目标：派多少由秘书定（保险丝 200 个没做完的），派出即全部开工，同时真正向模型发请求的有几个由系统按接口承受力自动调节（§3.2），写法上支持「一份模板加一批条目」，大批量回来的结果不撑满主人的对话。

## 2. 现状（代码里的事实）

| 位置 | 事实 |
|---|---|
| `tools/sub-agent.ts` `dispatchSubAgents` | `rawTasks.length > 10` 直接拒；`max_concurrent` 夹在 1–10，默认 5 |
| `sub-agent-roster.ts` `spawn` | 再夹一次 1–10；`startNext` 按「running 数 < 上限」逐个开工；`startQueued` 只留最后一次 spawn 的闭包（所以后一批改了上限，前面排队的也跟着用新的） |
| `tools.ts` `dispatch_agents` | 说明里写「1-10 个」「默认 5，范围 1-10」 |
| `ai.service.ts` | 没有任何进程级的请求缓冲池。`chatWithToolsStream` 里 429 最多重试 5 次，退避 5 秒起翻倍、单次封顶 60 秒（或按 `Retry-After`），算下来两分多钟就放弃，然后换模型或报错。派得多时一分钟的限流窗口还没过，一批伙计就可能一起放弃 |
| `sub-agent-roster.ts` `recordStep` / `runExisting` | 每个伙计每一步都 `onProgress(this.list())`：每次整份花名册拷贝一遍（含每人全部步骤）再推给界面，是 O(伙计数 × 步骤数) 的重复推送 |
| `tools/sub-agent.ts` `formatKnock` | 每个伙计做完敲一次门，正文带完整结果（超过 8000 字才落盘取摘要）；200 个 = 最多 160 万字进主人对话，且主人可能被敲 200 次 |
| 本机命令并发 | 没查到进程级的上限，待核实（见 §7） |

## 3. 设计

### 3.1 去掉数量限制，加保险丝

- 删掉「一次最多 10 个」和 `max_concurrent`（参数不再出现在工具说明里；旧调用若还带，忽略）。
- 保险丝：花名册里 `pending + running` 的伙计数 + 本次新派数 > 200 → 整次退回，错误里写清当前有多少没做完、上限是多少。常量放花名册模块，一处定义。
- `spawn` 不再按数量排队，`startQueued` 删除：全部立刻 `startChild`。要不要等位由 3.2 的缓冲池决定，发在每一次模型请求上，不在「伙计开不开工」上。仍失败的伙计如实报失败，主人能看到并重派。

### 3.1b 伙计被限流时更有耐心

伙计是后台干活，没人当面等，慢一点比失败好。缓冲池只按并发调节、不数字数，每分钟字数超限仍会有，这是第二层兜底。

- `ChatStreamOptions` 新增 `rateLimitMaxRetries`；`ai.service.ts` 里 429 重试次数由它决定，不传仍是现在的 5。只改 429，不碰网络错误和 5xx 的重试。
- 建伙计时由 Agent 传 20：按「单次封顶 60 秒」算，约 15–20 分钟才放弃，足够跨过好几个一分钟的限流窗口。账户欠费、密钥无效这类等也没用的，仍按原来的判断立刻报错，不重试。
- 等待期间界面沿用现有的重试等待卡：第几次、还要等几秒；伙计行上能看到「限流，等待重试」。
- 与缓冲池的关系：撞 429 要等重试时先放掉名额，重试前重新排队（见 3.2 接入方式），所以耐心等待的请求不会一直占着名额。
- 刻意不做：不让你当面的请求也这么有耐心；不改 5xx / 529 的重试；重试本身怎么用 `Retry-After` 不改（缓冲池那边另用它决定缓多久）。

### 3.2 模型请求缓冲池（`ModelRequestBuffer`，新文件；用户称它「自适应缓冲池」，不是固定数字的闸门）

> 2026-10-20 先议过暂缓、用伙计耐心＋错开起步兜底，后来判断兜不住：伙计耐心重试会一直占着额度，用户自己当面的请求（只有 5 次重试）会被挤得失败；一批伙计同时重试也不会收敛。所以做，但保持下面这个小版本。它按并发和限流反馈调节，不数每分钟字数；每分钟字数的精确节奏仍是想法本里「模型每分钟用量超限时，别只甩一句报错」那条。

位置：`electron/services/model-request-buffer.ts`（与 `ai-request-budget.ts` 同级），进程内单例，`ai.service.ts` 调用。目标是把它做小：一个计数、一条队、两条调节规则（放多少、何时放）。

**为什么放在请求层而不是「同时几个伙计活着」**：伙计大部分时间在等本机工具（网页、命令、远程机器），不占模型接口。若按「活着的伙计数」限，一个要等长工具的批量任务会被白白压低。限的应该是**同时在途的模型请求数**。

**管所有发往模型的请求，不只伙计**（2026-10-20 与用户确认）：额度按账号 + 模型算，不按谁在调用算。仓库里发往模型的 HTTP 只在 `ai.service.ts` 一处，一道缓冲池覆盖全部调用方（对话、取标题、知识重排与整理、记忆压缩、命令行、压测）。TTS、语音、本地嵌入是别的服务，不在里面。

**留下的四件事**：

1. **按分组计数**：键 = 接口地址 + 密钥 + 模型（只在内存里拼，不落盘不进日志）。每组有一个「在途数」和一个「窗口」，在途数到了窗口，后来的排队。
2. **用户当面等的请求不排队**：直接放行，只占一个在途名额、也参与「被限流」的判断。不传标记的调用方一律按这一档（默认值是故意的：新调用方忘了标，也不会被排到伙计后面）。**由此，缓冲池即使有 bug 也最多让伙计和后台变慢，不会卡住用户自己的对话。**
3. **排队的只分两档**：已经开工的伙计接着发的请求排在前面，其余（伙计第一次请求、关切、唤醒、整理）排在后面；同档先到先得。目的有两个：一批伙计陆续交卷，不是齐头并进最后一起交；同一个伙计接着发的请求前缀就是它上一轮的对话，模型接口的缓存还热（通常几分钟过期），排在新伙计后面久了缓存就凉了，白白多付一遍。
   - 开局那一波相同前缀的伙计，头几个会在缓存写好之前同时发出而未命中，200 个里只占一小撮；不为此专门做「先放一个暖缓存」，端到端时看命中率，不够再说。
4. **自动调节：有两条，都由报错的情况决定**（2026-10-20 用户提出：这不是一个固定数字的闸门，是按报错情况决定放不放下一个的缓冲池）：
   - **放多少（窗口）**：起步窗口 8。没被限流过之前，每成功一个窗口 +1（等于每一轮翻倍，很快爬上去）；被限流过之后，每成功一整个窗口才 +1。被限流时窗口减半，最小 1。
   - **何时放（缓一缓）**：被限流（429 或 529 过载）后，这一组先暂停放行排队里的请求。暂停多久：接口给了 `Retry-After` 就用它；没给就从 3 秒起，连续被限流每次翻倍，封顶 60 秒；只要有一个请求成功，就归零。暂停结束后窗口已经减半，只放少量出去试探；成功再慢慢放开，又被限流就再缓、缓得更久。当面请求不受暂停影响。
   - 为什么两条都要：每分钟用量这类限制，一旦撞上，接下来这一分钟剩下的时间里发什么都会被拒；只收窗口、仍然立刻放下一个，会一路撞到分钟翻页。先缓一缓才对。
   - **恢复只认缓一缓之后放出去的那个探路请求的成功**：缓之前已经在路上的请求，回来是成功还是失败，都不当作「接口恢复了」。暂停期间路上没有新请求，必须靠探路的那一个拿到结果才继续放。
   - **开头不是一次全放**：用户的直觉是「一直放，报错了就都缓缓，等正确返回再继续放」，这就是这套规则；只补一处：报错要一个来回才回得来，这段时间里放出去的会超过接口的承受，所以开头从小窗口起步、每成功一批翻倍，而不是 200 个一起冲。
   - 同一批请求同时撞上只算一次：每次调整就换一个「代」，只认在这一代里放行的请求撞上的限流，免得一批 429 把窗口减到 1、暂停翻到封顶。
   - 窗口没有固定上限，实际在途数受需求自然限住。起步窗口、暂停起步值、增长节奏用模拟压测定，不凭感觉。

**刻意不做**（想简单，这些先不上）：

- 不做四五档优先级；不区分关切和伙计谁先。
- 故障转移换了模型档，名额仍记在原来的键上，不换键。
- 不做超时回收名额的看门狗：放名额幂等、每条退出路径都有单测，不靠兜底。
- 不预测限流、不做每分钟字数平滑（那条想法单独留着）。

**接入方式：三处收口，不碰重试**：

- 一个请求从进入方法到最终交出结果，同一时刻最多占一个名额。**放名额是幂等的**（请求持有一个许可，放过就清空，重复放无副作用），所以不怕「某条退出路径忘了放或放了两次」。
- **撞 429 要等重试时，先放掉名额，重试前重新排队**：否则伙计耐心重试时一直占着名额，窗口缩小后又没人管得住重试的那一波。网络错误、5xx、视觉降级、换模型这些重试仍占着名额不放，不改它们的逻辑。
- 三处各加「入口取名额、出口放名额」：`chatWithToolsStream` 和 `chatStream` 在各自已有的收尾函数里放；`chat` / `chatWithTools` 在共用的请求包装外面套一层。撞 429 的那几行各加两句：「告诉缓冲池被限流了」「放掉名额」，重试前（发请求之前）再排队取名额。
- 排队中点停止：从队里拿掉，立刻按已中止收尾。
- 等位期间对调用方的通知：新增 `onBufferWait(waiting: boolean)`，沿用重试等待卡的展示通道，伙计行上显示「等模型空位」。
- 标记由调用方传：`ChatStreamOptions` 新增 `bufferPriority`（`urgent` / `continuing` / `queued`）。Agent 构造伙计时设 `queued`，伙计发过一次请求之后设 `continuing`；关切、唤醒、整理类设 `queued`。

### 3.3 一次派出的两种写法

`dispatch_agents` 参数调整：

- `tasks[]`：老写法，每个伙计一份 `description` + `prompt`（保持兼容），带多少对话仍默认全带。
- `batch`：`{ instruction, items[], fork_turns? }`。每个 item：`{ name?, description, input }`；实际交给伙计的 prompt = `instruction` + 换行 + 本条目的 `input`。不做占位符替换，纯拼接，没有模板语法要教。
- `batch` 的 `fork_turns` 与 `tasks` 用同一个默认（全带），不另立一套默认（2026-10-20 用户提出：全带的话一批伙计开局的前缀一模一样，能复用接口的缓存，不必为省字数去不带）。秘书按活选 `none` / 最近几轮 / 全带，说明书只写事实。
- **兄弟伙计的开局前缀要完全一致**，缓存才吃得到：身份说明、工具清单、带过去的对话都不能含每个伙计各不相同的东西；名字、分工、本条目这些各不相同的内容只放在最后那条任务指令里。先核实现状（§7）。
- 两个至少给一个，可同次混用，合计进保险丝。
- 说明书只写事实：两种写法各自是什么、**没做完的伙计总数不超过 200（含本次新派的），超了整次退回**（2026-10-20 用户提出：要告诉 AI，免得撞上才知道）、同时发几个请求由系统按接口情况调节、排队的会在轮到时发出、每个伙计各自占用对话上下文和费用。不写「该怎么选」。
- 上限数字只在花名册模块定义一处，说明书文案从它取，不手写第二份。
- 每次派出成功的回执里，写一句现状：「现在没做完的共 N 个，还能再派 M 个」。退回时的错误也写同样两个数。AI 不用凭印象数自己派了多少。

### 3.4 大批量回执

- **长结果落成文件，对话里只留一小段加位置**（2026-10-20 用户提议）：已有的落盘路径本来就是这个做法——结果超出门槛就写进这场的中转目录，对话里只留「共多少字、存在哪、尾部一段」，主人用 `read_file` 取。这次改的只是门槛：直接带回的字数上限不再固定 8000，而是随这场一共派了多少人收紧——人少时和现在一样（8000），人多时降到约 1000；各自上限乘人数保持在一个固定预算内。公式：直接带回上限 = 40000 ÷ 这一轮派过的伙计总数（含已做完的），夹在 1000–8000 之间。5 人及以下 8000，40 人起 1000。无状态，不用记「已经送进了多少」，也不会出现「前几位有全文、后几位只有要点」的不公平。
- **总览文件**：每个批次一份，每位伙计一行：名字、状态、结果字数、结果文件位置；伙计一做完就更新。主人要汇总几十个结果时先读总览，再决定读哪几个，或者用命令批量处理（筛选、拼接、统计），不必把全文读进对话。
- **合并敲门**：同一时间窗口（初值 1.5 秒）内做完的合成一次敲门，一条消息里列出多位。主人只被唤醒一次。
- **敲门不再掐断主人正在等的那次模型回复**（核实所得）：现在 `injectSubAgentKnock` 在主人处于「等模型」阶段时会直接中止那次请求、重新发。几个伙计时无所谓，几十上百个陆续做完时，主人每次刚开口就被打断、整段上下文重发一遍，又慢又费，还会和缓冲池抢名额。改成：敲门只进待处理队列，主人这次请求照常走完，下一个循环边界再领。用户自己中途补的话仍按原来的方式打断，不受影响。
- **`wait_agents` 的返回不再列全员**：现在每次返回所有目标的一行状态，200 人就是 200 行，每次等都重复。改成：一行计数（做完 / 在干 / 等模型 / 失败）+ 本次新到的那几位的名字；要看全员去读总览文件。领取语义改成一次领走所有已到的敲门（和合并敲门一致）。
- 主人不在跑时敲门直接丢弃，这一点不改：还有伙计活着时主人不会收工（`runUntilIdle`），用户点停止则全员一起停。

### 3.5 进度刷新

- 核实所得：每个伙计每一步都会把整份花名册（每人全部步骤，**连每一步工具的完整输出**）放进主人那条派出步骤，经 `agent:step` 整条推给界面，并随会话落盘。200 人时每次推送和落盘都是几 MB 级。
- 推送合并（最多约 4 次/秒），一批伙计变化攒在一起推一次。
- 推送和落盘里的伙计步骤只留工具名、对象、状态，不带工具输出；伙计结果只带直接带回的那段和文件位置。批量写法里各人的指令只存条目部分，共同指令存一份。界面原本就不展开伙计每一步的完整输出，用户看不出差别。
- 界面这边沿用整条替换（现在就是），因为推送体积已经降下来；不另做局部更新协议。压测若仍卡再做。

### 3.6 界面

- 伙计折叠行：「N 个伙计：x 做完 / y 在干 / z 等模型 / w 失败」；点开按状态分组，只渲染可见部分（200 项用虚拟列表或分页）。
- 排队中的不再显示「还没开工」，改显示「等模型空位」。
- i18n：`zh-CN` 与 `en-US` 同步新增文案。

## 4. 不做

- 不加设置项让用户配并发数。
- 不做花费估算和确认。
- 不改伙计不能再派伙计、不能自己找人确认这些现有约束。
- 不做每分钟字数（TPM）的精确节奏控制：缓冲池只按并发和 429 调节；每分钟用量超限那条想法仍单独留着。

## 7. 核实结论（2026-10-20 动手前查过）

1. **本机命令并发**：没有进程级的节流，伙计各自起本机命令。这一期**不做**：批量活的大部分时间在等模型，缓冲池已把它们错开；命令本身重的（装依赖、全盘搜索）由秘书分批派。端到端时看本机负载，压不住再单列。
2. **「全带」的内存**：每个伙计拿到的是父对话清理后的新数组，但正文字符串共用一份，200 人多出来的是对象外壳，不是 200 份正文。不处理。
3. **敲门的几种落点**：见 3.4，要改两处（不掐断主人的模型回复、`wait_agents` 不列全员）。
4. **界面更新方式**：整条替换；体积问题在 3.5 解决。
5. **连接池监听数警告**（原来设 30）：第 3 步改成不设上限（在途数由缓冲池管），压测时看日志里有没有这条警告。
6. **缓存前缀**：系统提示词里的当前时间早已关掉，伙计的名字只出现在确认提示里，不进提示词；同一批伙计的开局前缀应当一致。端到端时记命中率验证。「缓存的字数算不算每分钟字数」各家不同，不预设。
7. **伙计结果的中转文件**：放在工作区中转目录，会按「中转文件保留天数」设置自动清掉，总览文件同一处。不另做清理。

### 第 1 步实测（2026-10-20）

- 模拟：接口同时只接 10 个、每个 2 秒，200 个请求。各自冲撞（不排队、撞了就按现有退避重试）撞限流 1900 次、977 秒做完；进缓冲池撞 12 次、53 秒做完（理论最快 40 秒）。已写成单测。
- 接线：起本地假接口测了正常结束、接口报错、限流后放名额再排队、排队中中止、暂停中当面请求直接发，名额都不漏。
- 真模型：命令行普通对话、智能体任务照常。命令行 `ai:stream` 改动前后都不输出，是原来就有的毛病，与本次无关。

### 第 2 步与 2b 实测（2026-10-20）

- 派 30 个全部立刻开工；保险丝装满 200 后再派整批退回，已在干的不受影响；回执带「现在没做完的共 N 个，还能再派 M 个」，超了的退回说明带上限与余量。
- 档位按会话类别写进会话策略表：任务、联络当面等不排队；关切、唤醒排队。伙计第一回排后面，之后接着发的排前面。
- 「整理」类后台请求（记忆整理、标题生成等走的是非流式请求）这一步仍按当面算，没有标排队；量小，先不动，端到端时看有没有必要。
- 伙计被限流最多重试 20 次（每次最多等 60 秒，约一刻钟），其余调用方仍是 5 次；用假接口测了「给 1 次就报错」「给 20 次能做完」。

### 第 4 步实测（2026-10-20）

- 总览改成**每一轮一份**（不是每批一份）：一轮里派过的人都在同一份里，一人一行，`wait_agents` 和派出回执都指向它，秘书不用记好几个位置。
- 每个伙计的结果全文都落文件（不只长的），总览里每行都有文件位置，便于用命令批量处理；对话里直接带回的仍按人数收紧（5 人以下 8000，10 人 4000，40 人起 1000）。
- 合并敲门做在等待处：主人闲着等、或在 `wait_agents` 里等时，第一声到了再等 1.5 秒，要等的都做完了就不再等；按停、用户说话立刻醒。待处理的敲门在循环边界本来就合成一条消息。
- 敲门不再中止主人正在等的那次模型回复；用户补话仍会打断（单测覆盖）。
- `wait_agents` 说明里「只有下一步被挡住了才等」与系统提示重复，删掉工具说明里的这一句。

### 第 5 步实测（2026-10-20）

- 超过 5 个伙计收成一行「N 个伙计：x 做完 / y 在干 / z 等模型 / w 失败 / v 已打断」，点开才渲染卡片，一次 40 个，可「再显示」。在缓冲里排队的卡片标「等模型空位」。
- 进度推送合并到每 250 毫秒最多一次（敲门、收尾时立刻补推最后一次），推送里每步只带工具名和参数，不带工具输出；批量写法的卡片只显示条目，共同指令只在派出参数里存一份。
- 落盘：60 个伙计的会话记录共 80KB，其中派出那一步 16KB。
- 起界面时发现：记录只追加新步骤，派出那一步落盘后进度还在变，做完重新打开看到的是落盘那一刻的数字。改成一轮里落过盘的步骤被原地改过时，收尾保存整份重写（单独一个提交；动到对话记录的保存接口，只多透传一个已有的「整份重写」开关）。

### 第 6 步实测（2026-10-20）

假接口：同时只接 8 个，超了回 429（Retry-After 1 秒），伙计每个 4 秒，主人每次 0.3 秒；60 个伙计，十分之一给长结果。

- 命令行：60 个全部交卷，长结果落文件、敲门里截断并带文件位置，总览 60 行对得上。
- 界面（`launchApp`）：折叠行、等模型空位、分页、做完后重新打开显示「60 做完」都对。
- **当面的请求被挤（§8 第 2 条）**：伙计占满接口时，主人自己的请求（当面等的）一次次撞限流，重试用到 4/5，差一次就失败。改成：第一次照旧直接发；被限流后重试排在所有排队的前面，窗口里有空位就发，不等暂停结束。之后同样的压法，主人只撞过 1/5 就过了。
- **主人开口太多**：主人回完话、手上已有敲门就在内层循环里立刻接着跑，没走到等待处的合并，60 个伙计时主人发了 39 次请求。改成接着跑之前，待处理的只有敲门且还有伙计在干，也先稍等 1.5 秒（用户说话、按停立刻结束）。主人请求降到 13 次，整轮请求从 168 次降到 94 次、撞限流从 8 次降到 3 次，耗时约减半。
- **按停**：派 60 个、做完 8 个时按停，其余 52 个显示已打断，之后接口不再收到这一轮的请求。顺带发现并修掉：按停那一刻手上还没领的敲门，被当成「用户排队的话」交回界面，界面把几条「[伙计 xx 完成]」拼成一条用户消息又发了出去。
- 真模型（deepseek-v4-1-flash，命令行沙箱）：24 个文件各派一个伙计读、一句话说明，47 秒出表，没有撞限流；主人中间等了四次。这一次模型选了每人各写一份指令（`tasks`），没用 `batch`，属于按活自选，不强求。
- 没做的：假接口没加「按每分钟字数限流」那一档——缓冲池不数字数（§4），这类 429 走的是同一条重试路径；「你在另一场任务里说话」没单独起第二场，主人自己的请求就是同一类当面请求，结论同上。
- 假接口让心跳唤醒也照派了一批伙计（假接口对所有带工具的请求都回派出），一度把统计搅乱；那是测试脚手架的问题，已改成只对用户那句话派。

## 8. 上线后再看（不阻塞这一期）

1. 各家接口被限流的表现不同：有的 429，有的变慢，有的直接断连。看日志里「Rate limited (429)」和超时的次数，决定缓冲池要不要把「连续超时」也当成限流信号。
2. 用假的限流接口压一次：200 个伙计在抢额度时，你当面的请求不排队、会不会仍因为接口真饱和而失败；若会，让当面的请求也多几次 429 重试。这一条在端到端（任务 6）里就压，结论记回本节。**结论（2026-10-20）**：会被挤，重试用到 4/5。没加重试次数，改成被限流后的重试排在最前面等空位（见第 6 步实测）。
