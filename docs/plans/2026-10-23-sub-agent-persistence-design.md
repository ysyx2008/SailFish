## 现状（读代码得出，develop `7bd0e899`）

- **寿命 = 主人这一轮**：花名册在每轮 `run` 开头新建（`agent.ts` `_subAgentRoster = new SubAgentRoster()`），`cleanupRun` 里 `abortAll()` 后丢弃。主人这一轮收工、用户按停止、关 App，名册和各人的内存对话一起没了。同一轮里失败或做完的人，`followup` 可以在原对话上接着跑（`runExisting`），这条路是通的。
- **挡板不止一处**（都是 `_isSubAgent`），逐一看该不该开：
  - `saveCheckpoint`（每轮工具调用后增量写）开头直接 return：**要开**（写新树）
  - 成功 / 失败两条收尾路径（`2272`、`3031` 一带）里的一整块：`saveSessionToHistory`、标题刷新、L2 记忆记账 `noteRunForMemory`、L3 向量索引 `indexConversationAsync`：**只开存盘这一件**，记忆和向量索引不给伙计（伙计不进长期记忆），所以不能把整块的条件一删了事，要拆出一个伙计专用的收尾存盘
  - 向任务监督汇报 `handleRunFinished`（`2317`、`3055`）：**保持挡住**，伙计不是用户任务
  - 首个标题 `scheduleInitialTitle`（`2633`）：**保持挡住**
- **主智能体怎么存**：`Conversation.toRecord` → `saveAgentRecord` → `saveSessionRecord`（目录 `history/agent/<日期>/<会话号>/`，`meta.json` + `steps.jsonl` + `messages.jsonl`，追加写、先写 jsonl 再写 meta、用磁盘行数当水位，崩溃安全）；然后更新**共用索引** `agent-index.jsonl`。watch / wakeup 走另一棵树 + 另一份索引（`history/watch/` + `watch-index.jsonl`）。
- **重开补占位**：`sanitizeToolCallSequence` 对缺结果的调用补「执行结果未记录」；进程内被打断补「操作被用户中断」。
- **主智能体已知的边界缺口**：每轮检查点在工具**执行完之后**才写，崩溃发生在一轮执行当中时，那一轮要做什么不在盘上。

## 回答「会和主智能体共用一个日志文件吗」

不共用文件，但**直接放开挡板会共用同一棵树和同一份索引**：每个伙计有自己的会话号（`sub_<agentId>_<时间>`），会得到自己的一个目录，但 `storeForRecord` 除了 watch / wakeup 都归主树，于是 200 个伙计 = 主索引多 200 行，进最近对话、历史搜索、用量统计，违背 SPEC；同一块条件里还连着 L2 记忆记账和 L3 向量索引，一并放开会把伙计的对话写进长期记忆。所以做法是：**复用同一套追加写和崩溃安全的写法，写到单独的树，不进任何索引**（先例：watch 树物理隔离；专家团群聊 `<根>/<日期>/<会话>/<名字>.jsonl`，跟着会话删、按天清理）。

## 目标形态

### 存放

- 新树 `history/sub-agents/`，按「日期 / 主会话号 / 伙计名」组织，内容同主记录：`meta.json`（身份、状态、被中断标记、水位）+ `steps.jsonl` + `messages.jsonl`。
- 不建索引。主会话那边已经有一份每个伙计的小卡（`subAgents` 视图，随步骤落盘），名册重建时以它为目录，按名字去新树取正文。
- 复用 `session-persistence` 的追加写、水位、原子写 meta；需要把「目录怎么算」做成可注入（现在写死 `<根>/<日期>/<记录号>`）。这是对公共函数的改动，要有测试。
- 清理：随主会话删除、随日期过期（对照 `ExpertTeamChatStore` 的处理，含「会话已不在的孤儿」宽限）。统计和搜索只扫 `agent` / `watch` 两棵树，新树不在其中，要有测试保证不被扫到、不重复计用量。

### 不重复存主人的对话

伙计开局带着主人对话的一份拷贝（`fork_turns`）。每人存一份会存 200 份。只存各自新增的部分；开局那份按**内容指纹去重**，同样的开局只存一份，`meta` 里记指纹。续做时按指纹取开局、拼上各自的消息。不按「同一批」去重：开局是各人**开工那一刻**从主人对话里取的（`startChild`），排队晚开工的可能比先开工的多看到几条，同批里不一定相同；也不能只记「主人对话的前 N 条」做引用，主人对话压缩后前缀会变。

### 什么时候写

- 每轮工具调用完成后追加（和主智能体同一个点）。节流：同一进程内合并，异步写，不在主线程里同步写大块。
- 停止 / 失败 / 退出：写完整当前状态，悬空的调用标「被中断」，名册里状态标「被中断」。
- 退出 App 时来不来得及写：**要先查** Electron 退出流程里能否 await；来不及的话，退到「下次启动发现名册里还写着『运行中』就当异常退出」。

### 名册寿命

- 名册归**会话**所有，不是 `run`：`run` 结束不再丢弃，`cleanupRun` 只 `abortAll`（把还在跑的标为被中断）。
- 会话重开（`restoreFromHistory`）时，从主记录的小卡重建名册，状态为「被中断 / 失败 / 做完」，不自动续跑。
- 同一场里 200 个保险丝只数「没做完的」，已停的不占名额（现状如此，不变）。
- 续做 = 现有 `followup`：已停的人按名字取回存下的消息，装回 Agent，开新一段。

### 续做时告诉它什么（提示词，要审）

作为续做这一轮开头的一条系统注入，只陈述事实：

> 你上次被中断了（原因：用户停止 / 失败：<原因> / 退出 App）。中断时有 N 个工具调用没有记录结果：<工具名 + 对象>。磁盘上的现状可能已经变了，对话里记的只到上一轮结束。

程序异常退出（名册里还写着运行中）时：

> 上次程序异常退出，最后一轮的内容不明。磁盘上的现状可能已经变了。

不替它决定读什么、改什么。

### 主人的说明（提示词，要审）

两句事实，写进并行同事那一节，并改 `followup_agent` 的说明：

- 现状版（落地前也成立）：「派出的人只活到这一轮结束：这一轮收工、用户按停止或退出 App 之后，他们的对话就不在了，磁盘上已经写出的文件还在。他们没有终端窗，在本机干活。」
- 落地后版：「派出的人在这场会话里一直在名册上。被打断（用户停止、失败、退出 App）之后，状态是『被中断』，可以用 followup_agent 让他在原来的对话上接着干；他改过的文件不会被撤回，接着干之前他会被告知哪些调用没有记录结果。」

## 已知约束与风险

- **名册寿命改动最敏感**（任务 6）：`cleanupRun` 里的 `abortAll` + 丢弃现在是「这一轮收工的兜底」，改成跟会话走后，要保证「用户按停止所有伙计一起停」「还有人在干活主人不能收工」两条不变。
- **写入量**：200 个同时每轮写。各自的文件互不争用，但仍是主进程里的 I/O；要异步 + 合并，并在端到端里量一次。
- **老数据**：新增树和新字段，老会话读不到伙计小卡对应的正文时要当「没有存盘」处理（显示为做完 / 失败，不能续做），不报错。
- **回退**：`develop` 切回没有这个功能的版本时，新树被忽略，主会话不受影响。
- **与 `feat/worker-remote-hosts` 相邻**：那条目前只有方案文档，也改了 `agent/SPEC.md`，合入时 SPEC 可能有机械冲突；它实现后「远程伙计」的主机信息也要存进伙计的 meta，到时对齐。
- **文件改动的核对**：只靠「如实告知 + 它自己核对」，不做撤回、不做写前记账；任意命令（装依赖、迁移、git）无法自动判断做到哪一步。出现过「崩溃后重复执行不可重复动作」再补写前记账。

## 实现中定下的做法（对上面的补充）

- **名册仍然按「这一轮」建，不改成跟着进程活**：每轮开头新建名册，再把这场会话存下来的伙计按「被中断 / 失败 / 做完」装进去（没有活的对话）；这一轮结束照旧收掉。同一进程里的下一句话和重启后重开走同一条路，只测一条。续做时按存下来的记录重建一个新的伙计，对话接着原来的往下记，先前的 prompt cache 不再有。
- **专家团不跨轮恢复**：团里的话还留在群聊全文里，但团的运转状态（谁看到哪、叫醒几次）不存；恢复出来的专家作为单独的专家接着干，角色保留，不再在团里。
- **悬空调用用结构判断**：收尾时按消息结构（有调用、没有对应结果）找出没记录结果的调用，写进伙计的状态；不靠识别占位文字。
- **停止、失败、崩溃三种中断的现场不同**：停止和失败时对话里已经由现有逻辑补了占位结果，状态里另记下是哪几个调用；崩溃时检查点只到上一轮结束，状态还写着「在干」，重开时按「异常退出」处理。
- **存盘写盘量**：沿用主智能体的追加写，但每个伙计在内存里记着已写到第几条，不每次读整个文件数行数。首次存、或崩溃后重开才数一次磁盘。
- **清理的几个钩子（删会话、按天清理、清孤儿）与专家团群聊共用一套**，抽出一个通用的「跟着会话走的附属目录」，不再抄第二份。

## 实现结果（2026-10-23，已在分支上做完，等验收）

任务 1–9 都做完了，和上面方案不同的几处：

- **提示词只落地了「落地后版」**：这条分支把功能和提示词一起上线，没有单独发「现状版」。写在并行同事一节的一句话、`followup_agent` 说明的改动见 `prompt-builder.ts` / `tools.ts`。
- **停止时没记录结果的调用很少**：用户按停止时，正在跑的命令会被杀掉并带回一个「被信号终止」的结果，这一步在对话里是有结果的，所以状态里记的「没记录结果的调用」多半是空的；只有工具执行本身中途出了异常的路径才会留下。盘上的对话里能看到被停掉的那条命令和它的结果，叫醒前的说明照样告诉他「被中断」。
- **退出 App**：查了退出流程——它不会等智能体收尾（PTY 释放、后台命令被杀，进程直接结束），所以退出 App 和崩溃走同一条路：每轮检查点之外的最后一轮丢掉，盘上还写着「在干」，下次叫醒时按异常退出说明。没有为此另加「退出时等写完」。
- **叫醒时没有留下对话的**（第一轮还没做完就没了）：从他的指令重新开始，不假装有记忆。
- **休眠成员**：以前几轮派出的、已停下的，不占 200 名额、不进总览，名字也占着（新派的同名会加序号，避免盖掉他盘上的对话）。名册仍然每轮新建，第一次要用到时读一次盘。

### 实测

真起命令行进程 + 脚本化假模型（`node scripts/cli-e2e/sub-agent-persistence.mjs`）：

1. 终端里 Ctrl+C 停下，同一场里让伙计接着干：alice 带着停下前的对话接着做、先被告知被中断；没来得及做完第一轮的 carol 从指令重新开始。历史列表里只有主会话一条。
2. 命令行进程被 `kill -9`：盘上所有文件都读得出来，已做完的是「做完」，没来得及收尾的还写着「在干」；换一个新进程接着同一场会话，被叫醒的两位都先被告知「程序异常退出」，旧对话原样在前、新的接在后。
3. 一次派 200 位、各 3 轮工具往返：801 个文件、约 920 KB，整个命令 9.5 秒；1000 次检查点共约 350 ms、单次最长约 2 ms，状态文件 400 次约 70 ms；相同开局只存 1 份。日志里没有存盘相关的警告。
4. 日志里有两类和这件事无关的警告（主智能体的工具调用也有）：卡片收尾被重复调用一次；假模型不支持起标题的旁路请求。

### 代码审查后补的几处（同日）

- **按停止后马上又开口叫醒**：被停的伙计只是收到中止，最后一段对话要稍后才写完。下一轮开头先等上一轮没收尾的伙计写完盘（最多 5 秒，等不到就不再等），再去盘上叫醒，不读到半截的盘、也不会新旧两个实例同时动手。
- **没留下对话的伙计被叫醒后再次被叫醒**：他最初的指令也记进他自己的会话，以后再叫醒仍在。
- **对休眠的老伙计用「打断」**：回「他已经不在跑了」，不再说「没有这个人」。
- **清理删掉目录后**：对应的存盘人退下，迟到的写入不会把已删的会话目录重新建出来。
- **没改的审查意见**：开局存盘的序列化开销（实测一份 8 MB 的主人对话派 200 位共约 0.8 秒，现实里的 0.4 MB 约 36 毫秒，不值得为此加缓存）；英文提示里列表用顿号（全仓库通行写法，不单改这里）；叫醒后第一次存盘数一次磁盘行数（只在叫醒时一次）。
