# 知识库：目录印象召回 + 按需精读

## 首要边界：三级记忆是稳定资产

三级记忆（L1 任务记忆 / L2 知识文档与主机记忆 / L3 对话记录）是花了大量心血才调稳的，用户对现状满意。**任何知识库改造不得以它为代价。**

这条不是客套。本方案原始设计里有一处直接伸手到它上面：改 `hybridSearch` 的 RRF 融合。而 L2 主机记忆的召回（`searchHostMemories`）是直接调 `hybridSearch` 的，与知识库共用同一套融合逻辑和同一张向量表。改坏了不会报错，只会让召回悄悄变差。

**因此方案调整为：宁可给知识库单独开一条检索路径，也不要改公共的融合逻辑。** 卡片本来就存独立表，让卡片召回走自己的路，三级记忆那条路一行都不动。这样风险性质从「可能把已稳定的东西改坏」变成「新路子不好用就关掉回老路」——可回退的风险才是可接受的风险。

## 核心判断：知识库与硬盘文档的唯一本质区别是「自动到场」

每轮对话都会拿用户消息去检索知识库并注入上下文——冷启动进 system prompt，走 prompt cache 的连续对话也会注入到 user 消息（包在 `<sf_knowledge_refs>`）。所以自动到场不是启动时一次性的待遇，而是**持续发生在每一轮**。

硬盘里的文档 Agent 也能读（`file_search` / `read_file`），但那条路要求它**先想到去找、并且知道去哪找**。知识库不需要任何主动动作，靠语义自己浮上来。

这是知识库唯一的护城河，也是所有下游取舍的根。

> **2026-10-15 实测修正：对长篇文档，这条护城河目前基本没通水。** 拿一份真实监管法规（21 页 PDF）走完整链路实测：手动搜准得很，但自动到场那条路的 0.6 阈值把它几乎全挡住——「灾难恢复有什么要求」「客户信息保护」手动搜第一条就命中对应条文，自动到场 0 条。原因是法规正文段落对口语化提问的向量相似度落在 0.3 到 0.6 之间，而关键词那条腿排在这一刀之后，一并白干。
>
> 这不否定本方案，但**修正了它的推导依据**：原文认为问题出在「召回正文片段不如召回目录印象」，实际第一道坎在阈值。后来把 PDF 读取修好、法规正文完整进库之后同一批问题重跑，自动到场率一点没动（动的是引用准确度，46% → 75%），阈值这个结论因此得到确证。详见 [`done-2026-10-15-knowledge-recall-baseline-design.md`](./done-2026-10-15-knowledge-recall-baseline-design.md)。
>
> **但方向上的决断是不动那道阈值**（2026-10-15 用户定）：靠关联度自动送到眼前只是附带的，想不起来就想不起来。长篇资料该靠它自己意识到「这事得去知识库翻」然后主动去查——「灾难恢复有什么要求」本就是个该查制度的问题，不该等系统凭字面相似度把条文塞到它面前。所以本方案里凡是为「提高自动到场率」服务的部分不再是重点，重点转向「让它知道库里有什么、从而自己想得起来去查」。已落进 `electron/services/knowledge/SPEC.md` 的设计目标。

### 推论一：入库门槛应该更高，而不是更低

每一份入库的东西都在参与此后每一轮对话的召回竞争。垃圾进去不是静静占磁盘，而是在真正相关的内容旁边抢召回位、抢 token 预算。

由此得到一条用户可验收的入库判据，也是硬盘与知识库的分界线：

> **这份东西，值不值得在我没提它的时候被 AI 主动想起来？**

值得就入库（热层），不值得但以后可能用就留硬盘让 Agent 需要时自己翻（冷层，零常驻成本）。

### 推论二：劣化的机制是坑位排挤，不是体积膨胀

当时的自动召回实参：每轮取 **5 条**片段、相似度阈值 **0.6**、RRF 分数下限 **0.02**、整体 **2.5 秒**超时（超时直接跳过召回）。条数、相关性、耗时三道闸都在，成本侧基本可控。

但正因为坑位固定为 5 个，垃圾入库不会撑大账单一个字节（账单完全正常），只会把本该进前 5 的正确内容挤下榜。**用户观察到的现象只会是「秘书答得不如以前准了」，查不到任何指标恶化。** 这是这类系统最危险的失效方式：限量把成本风险转化成了隐性的质量风险。

因此防劣化的抓手不能是「再限紧一点」（再紧就开始漏真东西），只能是：入库门槛、Agent 入库物可见可清、召回域隔离、掐掉最强的污染物（见下条）。

### 推论三：原文优先于转述

专业知识（行业监管规定、公司制度）必须**原文入库**，AI 的转述不能替代原文。

理由是这类知识的价值全在精确条文：条款编号、「不得超过三十个工作日」、除外情形。转述必然丢条款号、丢例外条件、把「原则上」写成「必须」。而一旦转述版进了库，此后每一轮召回喂给 AI 的就是那个失真版本，错误被永久固化，还带着权威的样子。

更要命的是：**转述版最擅长赢得召回竞争**——它是围绕问题组织过的加工文本，语义上与提问极其贴合，必然过阈值，还很可能排在原文前面。最会赢的恰恰最危险。

成本上原文入库也更优：文档解析直接进库，不经过 Agent 上下文；让 Agent 转述反而要先把全文读进来，贵且有损。

AI 的加工物应该放在**导航层**（这份文件讲什么、适用范围、关键条款在哪），指向原文。原文负责准确，导航负责让 AI 快速判断该不该翻。

### 推论四：派生物必须可追溯到来源版本（2026-10-15 补）

起因是看到别的产品做「AI 自动 Wiki 生成」，用户一句话点破：Wiki 能被修改，可信度就有问题。

往下挖一层：权威性来自三件事——**不可变、有确定出处、能被第三方核对**。原文三样都有（哈希可证没被动过、谁发的何时生效、能翻到第几条）；AI 生成的派生物三样都没有，它是写出来的、随时会重新生成、被改过也看不出改了什么。所以派生物天生只能当索引，不能当依据。

由此立一条规矩：**派生物必须永远能指回它所基于的那一版原文，并且能看出它是否已经和原文脱节。** 方案里记录来源内容哈希的机制原本只为「换版要重建」而设，现在它的真正意义是可信度的锚——没有这个锚，卡片就是一段来历不明的文字。

同时也划清了与那类产品的差别：它们比的是知识加工能力，我们守的是「交给秘书的原件不会被它自己的转述悄悄替换」。对一个装在用户自己机器上、用来放公司制度与监管原文的私人应用来说，这不是技术选择，是可托付性的组成部分。

## 方案：召回从「正文片段」改为「目录印象 + 按需精读」

召回主体换成「路径 + 标题 + 一行卡片摘要」，Agent 拿到线索后自己决定 `get_knowledge_doc` 读哪份原文再作答。

### 为什么这样更好

- **绕开分块难题**。腰斩、丢失「前款所称」的指代，这些麻烦全都源于「片段就是最终依据」。改成线索之后，Agent 读的是完整原文带上下文，分块准不准就不再决定答案对错。
- **可核对天然成立**。真读了原文，引用「第几条第几款」是自然的；而片段召回只带文件名和字符偏移，答不出条款位置。专业场景下这两者不是一回事。
- **坑位从 5 个变上百个**。一条路径+标题只有几十字符，同样预算能给上百条印象，零和排挤基本不成立。
- **污染代价骤降**。垃圾最多占一行标题，且 Agent 看标题会自行判断相关性，不像正文片段那样以事实姿态直接躺在上下文里。转述污染的杀伤力也随之下降，因为最终依据是打开的原文。

### 前提：必须有检索卡片，否则会哑

**标题的语义太稀薄，纯标题召回会把召回率打下来。** 向量检索吃的是语义面积——正文片段召回得准，恰恰因为它字多，「三十个工作日」这类词都在正文里。真实文件名是《关于进一步规范XX管理工作的通知》，而用户问的是「报销超过多少要审批」，两者语义距离很远，很可能压根匹配不上。那就从「给半条规定」退化成「根本没告诉我有这份文件」，更糟。

所以每份文档必须配一份**检索卡片**：标题、路径，加一段说明它讲什么、管什么范围、涉及哪些关键概念和常见问题。**用卡片做向量索引**，召回时只返回标题+路径（顶多一行摘要）。检索有足够语义面积去命中，上下文里只留线索。

「AI 加工物只做导航」从洁癖式原则变成了技术前提。

### 召回不能单腿站在卡片上

卡片写歪是**最隐蔽的失效**：《差旅管理办法》被摘成「关于办公用品的规定」，那份文档就从检索里彻底消失了，而且不会有任何报错——用户永远不知道 AI 为什么「不知道」公司有差旅制度。

两条防线：

1. **向量腿走卡片，BM25 关键词腿继续走原文 chunk。** 两条腿不同源，卡片写歪时字面命中还能把文档捞回来。已有先例可参照：主机记忆就是向量存密文、BM25 存明文。
2. **卡片必须在界面上看得见、能改、能重新生成。** 这是唯一的人工纠正入口。

### 别全押在目录印象上

最大的实际风险是 Agent 偷懒——拿到一堆标题，觉得「我大概知道这事」就不翻原文直接答，那比拿着片段回答更差。

对策是混合：默认给宽而便宜的目录印象，**同时保留一两条相似度极高的正文片段**。简单问题不用多跑一趟，复杂问题有线索去深挖；再配上「只拿到标题时必须先读再答」的提示纪律。

好消息是这条纪律**可以端到端验证**：它是行为不是语义，跑真实任务后检查调用序列里有没有「先读原文再作答」即可。

## 卡片由闲时后台自动生成（梦游）

入库时不必读全文，只登记文档并标记「卡片待生成」，用户那一刻的交互零成本；卡片留给闲时慢慢补。这也是秘书「晚上整理档案室」的隐喻落地，与「秘书是活人、有自主循环」的产品定位一致。顺带说，闲时是桌面常驻应用独有的便宜午餐，云端 chatbot 没有「闲时」这个概念。

设计要点：

- **必须是持久待办队列，不能靠 AI 即兴想起来做**。即兴发挥会漏、会重复、无法验证。状态位直接挂在文档记录上（pending / generating / ready / failed），队列就是「状态为 pending 的文档集合」——`documents.json` 已是 tmp+rename 原子写，天然崩溃不丢；进度就是按状态计数；启动时把残留的 generating 重置为 pending 即可续跑。**不需要新建队列文件。**
- **不走 Agent ReAct**，直接单次 LLM 调用，确定性可控，形态参照 `context-knowledge.ts` 的 `updateWithLLM`。开放式 ReAct 不适合确定性批处理。
- **成本要有闸**。一份卡片要通读原文，几千到几万 token。一次倒进两百份监管规定，能连着烧掉几百万 token 而用户毫无察觉。需要每轮与每日配额；优先级不按入库顺序，而是**优先处理最近被检索碰到过但还没有卡片的文档**（按需驱动优于先来后到）。
- **用便宜或本地模型**。这是「读长文写摘要」的机械劳动，不需要旗舰模型；这直接决定它能不能长期跑下去。
- **文档换版要让卡片失效重建**（内容哈希已有基础），否则会出现「卡片说旧版、原文是新版」的错配。
- **触发不要挂心跳**——心跳只在「觉醒模式」开启时启用，用户没开就永远不整理。应走后端初始化完成后 defer 启动的低频定时器，并尊重现有静默时段配置。

这条队列一旦建起来，卡片只是第一个消费者：归档路径建议、重复与过期文件发现、文件间冲突发现都能挂上去。但**先只做卡片，别一上来铺开**。

## 树状层级的意义是召回域，不是文件浏览器

最初的想法是「像资源管理器一样浏览，让 AI 能翻阅自己的知识库」。这个理解需要修正：主动翻阅本来是硬盘的活儿，知识库的价值在自动到场。

**树的第一价值是给自动召回划定范围和纪律**——层级就是可控的召回域。当时的自动召回是全库一锅端：接口上能按主机和标签过滤，但每轮自动注入这条路径上没人传参，结果是用户写代码时，个人健康记录和公司差旅制度在同一个池子里跟技术文档竞争。有了树，「当前在聊什么」就能映射到「该在哪棵子树里召回」。

这么定位之后，这个大改动比「给 AI 一个文件浏览器」值当得多——它修的是每一轮对话的质量和成本。可枚举地图、辅助归档是附带收益。

另外路径本身就是用户亲手写的分类，是零成本、比向量可靠得多的语义信号。

**章节级延伸**：一份三百页的监管汇编，光知道「有这个文件」没用——打开也读不完，上下文装不下。索引层需要能到章节（路径 → 文件 → 第四章 报销审批），这其实就是树延伸进了文档内部。`chunker.ts` 已有 Markdown heading 栈解析（`parseMarkdownSections`）可复用，非 Markdown 文档还需要新的结构识别。

## Agent 的知识库权限边界

现状是：Agent 能查（`search_knowledge` / `get_knowledge_doc`），但归档完全靠用户手动切到设置界面上传。而产品理念里知识库已被定义为秘书的「档案室」，且写着「秘书应主动维护记忆，而不是等用户手动告知」——**现状是自相矛盾的：一个连自己档案室都整理不了的秘书，本质上是个搜索框。**

所以给 Agent 管理能力的性质不是扩张产品边界，是**补齐一个已经许下的承诺**。

- **给「添加」**：只收本地路径，内部解析后入库，**全文不进 Agent 上下文**——这是入库工具的全部意义。打来源标记，可带路径与标签。现有的变通路径（Agent 读全文 → 用户手动入库）要把整份 PDF 灌进对话，几万 token 还得手动操作，本身就是浪费。
- **给「列目录」**：只返回路径 + 标题 + 一行摘要，不返回正文。
- **删除分权**：Agent 自己入库的可自主删（word/excel 技能保存样式模板时已经在这么做）；删用户上传的必须走危险操作确认。知识库**没有回收站**，删了只能靠备份恢复。
- **运维口一律不给**：清空全库、导入导出、重建索引、切换嵌入模型留在设置界面。误触代价大且不可逆，Agent 没有任何需要它们的场景。
- **可见性是自动化的前提**：Agent 入了什么，用户要能一眼看到、能批量撤掉。自动化没有可见性兜底，只会加速劣化。

## 明确不做

知识库不能膨胀成第二个产品。它不需要富文本编辑、在线预览美化、版本 diff、协作。**它只有一个使命：让正确的资料在正确的时刻自动到场。** 凡不服务这句话的功能都不该做。

> 两处需要重看的变化：
>
> - **记忆设置页已改**（维护收成备份恢复、清空须打字确认、可改每份字数上限）。UI 落点仍是它，但内部结构变了。
> - **L2 记忆更新机制已重写，本文一处锚点作废**：它改成「接在刚跑完的那场对话后面问（吃缓存）+ 只交变化的补丁」，`context-knowledge.ts` 的 `updateWithLLM` **已不存在**，新实现在 `agent/memory-refresh.ts` 与 `knowledge/memory-patch.ts`。本文原先建议卡片生成参照 `updateWithLLM`（独立一次调用、整篇重写），该参照失效——「接着对话问」不适用于卡片生成（批处理没有对话可接），但**「只交变化的补丁」思路应当采纳**：记忆侧的实证教训是整篇重写不仅把最贵的输出花在原样抄写上，还会把没打算改的地方写坏（已出现断成半句的记忆）。卡片重生成同理。

- **RRF 融合按 chunk id 合并**（`storage.ts` 的 `rrfFusion`，以 `result.id` 为 key）。卡片腿返回卡片 id、BM25 腿返回 chunk id，同一文档无法叠加分数。原方案要改成按 docId 融合，但那是所有检索的公共路径（主机记忆、`search_knowledge`、L3 对话检索都走它）——**这正是本文首要边界要求绕开的地方，应给知识库独立路径而非改公共逻辑**。
- **LanceDB 表 schema 由首条记录推断，没有列级迁移**（`VectorStorage.initialize` 建表处）。加列只能 drop 重建。因此：卡片应存**独立表**（老向量表完全不动，老用户不需要全量重嵌入；卡片是可再生派生物，表坏了重生成只花钱不丢数据）；层级路径**只落 `documents.json`**，过滤时按 docId 反查文档索引拿路径——因为 hostId / tags 过滤本来就是内存后滤（`formatResults` 内），零 schema 改动。
- **`loadDocumentsIndex` 是裸 `JSON.parse`，没有 normalize**（`KnowledgeService.loadDocumentsIndex`）。新增字段必须配 `normalizeKnowledgeDocument` 补默认值，否则老用户数据会出现 undefined。`electron/utils/normalize.ts` 当时没有任何 knowledge 相关函数。
- **自动召回只限条数不限体积**。5 条不截断，上万字符会发生（L4 摘要那条链路专门为此做了句边界裁剪防护）；而 Agent 主动调 `search_knowledge` 反而每条截断到 1000 字符。**这个不对称是独立于本方案的缺陷，可以单独修。**
- **知识库共用类型全在后端** `electron/services/knowledge/types.ts`，`shared/types` 与 `packages/shared-types` 均无知识库类型；前端组件、`preload.ts`、`vite-env.d.ts` 各自内联重复了一遍文档形状。这是历史债务，按项目规则应迁到 `packages/shared-types/src/knowledge.ts`。
- **`src/components/KnowledgeManager.vue` 是没人引用的死代码**，真正在用的是 `src/components/Settings/KnowledgeSettings.vue`（由 SettingsModal 挂载，标题「记忆与知识库」）。UI 改动只应落在后者；前者的清理属于重构，独立做。
- **不存在通用持久任务队列**。最接近的可照搬模式是 todo 迁移 marker（原子写 JSON + 状态机）与 `repairIndex` 的 batch/checkpoint。
- **`notifyIdle` 定义了但从无调用方**（`AppLifecycleSensor.notifyIdle`），没有任何「用户空闲」检测。心跳默认 30 分钟且只在觉醒模式开启时启用。
- **没有按任务类型指定 AI profile 的配置**。`runAssistant` / `chat` 都支持传 profileId，但 wakeup 是跟着全局 activeAiProfile 走的，也就是后台任务默认在用旗舰模型。要让卡片生成用便宜模型，需要新增配置项。
- **卡片必须有降级路径**。卡片表为空、卡片未生成、卡片表损坏三种状态下召回必须能回退到正文片段——新装用户和队列没跑完的用户都处于这个状态，降级失败等于知识库直接哑掉。

## 测试策略

CLI 拦截 `require('electron')` 复用全部后端服务，回归跑在临时沙箱并从桌面借用 AI Profiles，所以 `knowledge:add` → `knowledge:search` 是**真实 embedding + 真实 LanceDB 的端到端语义检索**，不是 mock；有 Key 时 LLM 调用与完整 Agent 任务也能真跑。

**除 UI 与主进程响应性外，整条链路都能自动端到端验证**：入库后的路径与来源标记、卡片生成与换版失效、召回输出形态与字符预算、卡片表清空或损坏时的降级、老数据字段补齐、配额不被突破、删除权限分支、以及前面说的「Agent 拿到印象后是否真去读原文」这条行为纪律。

真正测不了的只有两项：**UI**（vitest 是 node 环境无 jsdom，CLI 也没界面）和**主进程响应性**（卡片生成是否卡窗口，CLI 无窗口，只能桌面端实测）。

**卡片质量有可测代理**：卡片写歪的唯一后果就是该文档在检索中沉底，所以基准命中率就是卡片质量的代理指标，不需要人逐份读卡片。

### 召回基线（独立价值，不依赖本方案）

一组固定语料（15-30 份代表性文档，含真实监管文件脱敏样本）+ 标注好期望命中文档的问题集（可让 AI 读文档自动出题、用户只做确认或否决），做成 CLI 子命令输出 top-1 / top-5 命中率并纳入回归。

**它的定位不是本方案的前置工作，而是保护现有成果的工具。** 现在这套记忆好到什么程度只存在用户的体感里；一旦有人动了检索参数，没人能证明是变好还是变差——这正是「劣化无声」本身。把体感变成数字存档之后，将来任何改动都得先过这条线才有资格上，调阈值、条数、融合权重也能立刻看出动了哪条防线。

它纯只读、不改任何行为，可以在完全不做本方案的前提下单独存在。

## 待议：人改过的派生物，遇上原文换版怎么办（2026-10-15 提出）

方案里有两条都对、但在这一点上互相撞的要求：卡片**必须可见可改**（写歪会让文档在检索中静默消失，人工纠正是唯一出路），以及原文换版时卡片**必须失效重建**。

冲突在于：人校对过的卡片，身份已经从「原文的派生物」变成「人的断言」——它其实比 AI 写的更可信，但与原文的自动同步关系断了。原文换新版时，重新生成会白费人工校对，保留则会跟新版原文脱节。

倾向的方向（未定）：记一条「是否经人校对」的状态，换版时不覆盖人的修改，而是标明它基于的是旧版、请人重新确认。本质上是让可信度等级与同步状态都可见，而不是二选一。

## 待议：与 L3 的关系（2026-08-21 提出，尚未展开）

问题：卡片召回是不是在替代 L3，或者至少该跟 L3 融合？

初步判断如下，待专门讨论。

**不是替代，因为内容来源不同**：L3 是 Agent 自己的经历（我做过什么），知识库是用户交给秘书的资料（我有什么文件）。两者互补，不可互换。

**但访问模式同源，而且 L3 才是先行者**：`indexConversation` 索引的不是完整对话正文，而是「用户任务 + 最终答案」这对摘要，要细节再去取完整记录——这本来就是「线索层 + 按需精读」。三级记忆里 L3 的定位也一直是「按需检索、不占日常 token」。反倒是知识库是那个异类：它不给线索，直接把正文片段灌进每一轮上下文。**所以本方案的本质是把 L3 早已验证的访问模式复用到知识库，不是发明新东西。** 这也从侧面说明这条路可行。

**真正值得讨论的融合点是线索层合并**：无论是一份监管文件还是一段过往对话，对 Agent 都是「我知道有这么个东西、跟当下有关、要不要翻开」。两者现在各自往上下文里塞东西、抢同一份预算与坑位；如果都变成线索，可以在同一个印象层里排队，由 Agent 统一决定翻哪个。

**融合的硬约束（先立规矩再动手）**：

- **权威性必须分层**。L3 里有做错的、过时的结论；知识库原文是权威资料。平权排队会导致 Agent 拿「上次我是这么干的」覆盖监管条文——与转述污染同类，但更隐蔽，因为经历读起来特别可信。
  - **2026-10-15 复核发现：这条在 L3 侧已经落地了一半**，见 `agent/SPEC.md`「自动召回的过往对话只是参考，不是用户的话」（2026-10-11）。起因正是这类事故：用户说了句含糊的「深度测试下」，召回贴上来很久以前的旧对话，模型拿它补全了意思并照着动手。解法比本文设想的更克制——**只写清事实**（系统按相似度自动检索的、不是用户提起的、哪天、这场还是另一场、当时用户说了什么、怎么收场），而不是另加「不许当成指令」之类的禁令。同时自动召回与它自己搜历史的结果已统一为同一写法，这对「线索层合并」是实质利好。
  - **仍缺的另一半**：知识库召回至今没有任何出处标注（输出仍是文件名加正文）。而本方案的「路径 + 标题」天然就是出处，落地时应当与 L3 那套写法对齐，别再发明第二种写法。
- **量级与生命周期不同**。L3 每次对话都在增长，知识库文档有限且由用户主动放入，两者的淘汰与压缩策略不可能共用一套。

## 为什么本期不做

用户对现有三级记忆满意，而这套体系是花大量心血才调稳的。原方案要改的融合逻辑是它的公共路径，风险性质是「拿一个已经满意的东西，去赌一个理论上更好的形态」，且劣化无声、没有基线可对照。在这个前提下暂缓是正确的成本收益判断。

## 如果重启，建议顺序

1. **召回基线**先行（纯只读，把现状变成数字，之后任何改动才有对照）。
2. **入库通道**（只给「添加」，不碰检索）——这道摩擦决定了库永远长不大，后面所有优化都无米可炊，而且它风险完全隔离。
3. **卡片存储与闲时生成**（独立表 + 状态位队列 + 便宜模型 + 配额）。
4. **卡片召回走独立路径**（不改公共融合逻辑），混合形态：目录印象为主 + 少量高分正文；同时补上自动召回缺失的字符预算。
5. **管理界面**（路径树、卡片可见可改、来源筛选与批量清理、队列进度）。
6. 之后才考虑：召回域隔离、章节级粒度、时效与版本（废止标记）、闲时队列承接归档建议与冲突发现。

顺序原则是「错了会让 AI 给出错误答案」的严重程度，以及「能不能可回退地上」。
