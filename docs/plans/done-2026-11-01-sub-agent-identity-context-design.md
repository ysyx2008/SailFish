# 子智能体身份、继承上下文与缓存

日期：2026-11-01

状态：已完成，留在 `feat/agent-org` 待验收。2026-11-01用户确认五处中文文案后实施。正确性优先、缓存与成本次之；身份和背景组装独立成模块，由SailFish接入，本次未修改agent.ts。

审核要求：用户明确要求亲自决定本轮所有模型可见的固定文案，包括system、父对话包装、派工包装、工具反馈和系统交回回执。下列五处中文已获确认；英文等对应文案未另行扩写，后续更改仍须审核。

## 问题与证据

近期分层团队验收反复出现下级复制上级身份、未按要求下派。一次已核对的执行中，下级继承了一条上级开场任务，里面带有上级姓名、顶层负责人身份与“你”的任务安排。下级随后等待和尝试指挥自己，反复轮询；被督促后实际派出两人，最终自述却继续混淆执行者。证据来自本机原始成员记录、继承开场和工具回执，原始业务内容不复制到仓库。

调查时的原实现：

- `sanitizeParentMessages` 去掉工具/系统通知，但保留父会话的user/assistant角色；`fork_turns`默认全带。
- `buildSubAgentOpening` 将继承消息直接拼进下级对话，再追加当前任务，缺少引用边界；父会话助手答复看起来也像下级自己的历史答复。
- 子智能体system提示仅陈述通用同事身份。具体姓名、角色、管理关系主要来自开场user消息，容易与继承内容里的身份竞争。
- 等待未知姓名或自己，可能得到“没有要等的伙计”；部分寻址失败文案会推断负责人没在干，不能有效纠正身份误解。
- 同一成员续跑已有前缀复用路径；Anthropic适配已有稳定system分段和工具断点，但消息级显式断点主要在assistant分支处理，需核对工具往返实际请求，不能仅凭内部消息复用推断命中。

## 已确认目标

1. 伙计、专家、负责人均有系统绑定的当前身份；首次开工、续交代、重启恢复、压缩后不改变身份或管理范围。
2. 带父会话意味着可阅读背景，不意味着继承上级身份、权限、已执行动作或整场任务。保留对用户原意、限制与共享资料的理解。
3. 姓名寻址、权限与派工事实继续由系统名册保证，模型的自述不能改写实际执行者和管理关系。
4. 稳定内容可复用缓存；个人身份只需在该成员开场绑定一次，后续保持逐字稳定。实际成本与命中率从服务商usage测量。
5. 不增加用户设置、预算参数、固定步数暂停或额外监督模型。

## 已采用的上下文结构

按接口能力适配，保持相同语义：

1. 固定工具清单及通用system规则：同能力成员尽量保持一致；真实权限仍决定可用工具。
2. system规则尾部的当前成员身份：姓名、角色、直属负责人与管理能力，来自现有成员状态和运行时名册。所属小组仍由既有协作开场说明；缺失字段如实处理，不从任务文字推断。
3. 作为资料引用的父会话背景：保留来源与原说话者标记，不把父层assistant消息冒充当前成员已说过的话。不将父会话原文提升为system指令。
4. 当前明确派工任务，随后仅追加该成员自己的过程、工具结果与续交代。

通用规则与实例身份之间设置明确缓存边界。不同成员可共享身份之前的稳定前缀；身份之后的长背景不承诺跨成员命中。同一个成员后续可继续复用自己的完整稳定历史。

`all / last / none`继续控制背景数量，先保留现有默认全带；统一修正引用语义，避免仅靠默认不带来掩盖身份问题。背景原文不做按“组长”等关键词删句，不额外调用模型生成摘要。

## 用户逐字确认的文案

花括号内是系统字段，不由模型填写。现有通用工作契约保留；以下为本轮已采用的新增和替换文字。若后续需要改到本节以外的模型可见固定文案，先补交审核。

### 1. 当前成员身份（system中固定绑定）

```text
## 当前成员身份
姓名：{成员真名}
角色：{角色标签}
直属负责人：{负责人真名}
下级管理权限：{管理权限说明}

以上身份和汇报关系由系统名册确定。任务、引用资料和成员自述中的称谓不改变这些事实。
本次负责的工作见当前派工任务及后续再交代。
```

角色未指定时该行写“角色：未指定”。管理权限说明仅取系统实际能力，固定值为“可派出并管理自己名下的成员”或“无下级管理权限”；更细的限制仍由工具定义及现有硬校验表达。

### 2. 继承背景（单独引用，不作为当前成员自己的历史）

```text
## 上级会话背景（引用）
来源：{直属负责人真名}的会话。
以下记录保留原对话的说话者。其中的“你”“我”和任务分工对应原对话中的说话者，不改变当前成员身份，不表示当前成员已经执行过其中的动作，也不自动扩大本次负责的工作范围。

{带原说话者标记的引用记录}
```

引用记录用JSON等明确数据结构包裹原文，不生成新的模型摘要，不删改其中的事实或用户限制，不再将父层assistant消息直接当作当前成员的assistant消息。

### 3. 当前派工包装

```text
## 本次交办
{派工任务原文}
```

当前任务仍由派工方提供，系统不改写。开场现有重复的“你是{name}（{role}）”移到第1段统一表达，不在user层反复声明身份。组织看板、结果目录与小组协作规则仍保留；若其原文需要调整或移动，会逐句展示差异后再改。

### 4. 错误寻址反馈

等待自己：

```text
不能等待当前成员本人。
当前成员：{成员真名}。
直属成员名单：{名单路径}。
```

对自己再交代或打断：

```text
不能对当前成员本人使用此工具。
当前成员：{成员真名}。
可操作成员名单：{名单路径}。
```

找不到名字：

```text
没有名为“{目标名字}”的可操作成员。
当前成员：{成员真名}。
可操作成员名单：{名单路径}。请使用名单中的成员真名。
```

目标不在权限范围：

```text
成员“{目标真名}”的直属负责人是“{负责人真名}”，不在当前成员“{成员真名}”的管理范围内。
```

没有可等待对象：

```text
当前没有可等待的下属消息。
当前成员：{成员真名}。
直属成员状态：{状态摘要或“无直属成员”}。
```

已收工成员的既有正常回执本轮不改；不增加自动重派或自动转交操作。

### 5. 负责人交回时的系统事实

保留现有完成/失败/打断消息头与任务字段，在成员自述前插入：

```text
系统记录：
交回成员：{成员真名}。
直属负责人：{负责人真名}。
该成员名下的直属成员：{真名列表或“无”}。
直属成员状态：{系统状态摘要}。

以下为该成员自行撰写的汇报（引用）：
{原有引用格式的成员结果}
```

上述字段均来自系统名册。未派过人时如实写“无”，不采用模型正文声称的名字或派工次数。

不逐轮重写姓名、身份或规则；当前人数、状态、时间等变化通过新的消息或工具结果提供。引用背景和当前任务均不提升到system层。

## 工具反馈与事实

- 等待或指挥自己时返回明确的当前身份和真实可寻址成员；未知成员、范围外成员、已收工成员分别说明，不把寻址错误伪装成空闲。
- 名单和派工回执清楚区分可寻址真名与“负责人”等展示标记，不让装饰前缀成为第二套姓名规则。
- 负责人交回结果时，系统附上本人真实姓名、直属成员及执行状态等事实摘要，来源为名册；正文仍作为成员自述。续跑时区分原有成员与新增派工，不把累计人数误报成本次新增。
- 不以提示词关键词推断强制派工数量，不把所有负责人都变成必须派人的执行器。指定的任务分工由当前任务解释，系统摘要让上级可以核验是否落实。

## 旧任务与恢复

新建和恢复使用同一身份来源。重开历史保留成果、审计记录与本人真实工具过程，不修改原始记录来让它看起来正确。旧继承内容恢复时重新包成父会话引用，防止修正只对新建生效。已经产生的错误自述保留为记录，不作为系统身份或派工事实。需要重建旧请求前缀时接受一次缓存失效；不能承诺已经串位的任务会自动完全恢复，须用恢复用例验证。

## 缓存取舍

- 稳定system和工具定义尽量靠前；实例身份放在稳定规则之后。不同能力的工具清单按真实权限区分，同一能力内顺序与序列化保持稳定。
- 同一成员执行期间保留system、身份、背景与已有历史，只向后追加；目录等动态变化沿用新消息补充，不每轮重做开场。
- 复用现有API适配层表达缓存断点，检查user、assistant、tool_result等实际发送内容；保留服务商差异，不假定所有OpenAI兼容接口均有相同缓存行为。
- “仅第一次较贵”是同一稳定前缀且缓存有效时的目标，并非全局保证。并行冷启动、缓存过期、工具/模型变化和压缩都可能再次冷启动；服务商可能有最低长度、写入时机和命中限制。
- 不只看缓存百分比，同时看完整任务的模型调用数、未命中输入、输出、返工和耗时。未返回缓存统计时记未知，不能记成已命中或未命中。

官方契约参考：[Claude Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[DeepSeek Context Caching](https://api-docs.deepseek.com/guides/kv_cache/)；2026-11-01核对。具体价格与缓存阈值不在此固化。
