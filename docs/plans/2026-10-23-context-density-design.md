# 上下文用量估算偏差：第一个请求不超限（2026-10-23）

状态：A、B 都已做完（2026-10-23），等验收合入。（B 已从「偏差倍数」改回「存真实用量」，与讨论一致）

## 起因

用火山 Deepseek 4.1 flash（窗口 110K）全面探测上下文管理（`scripts/probe-context-110k.js`）：压缩、交接、冷启动降级、大文件限额都接得住，唯一的真问题在估算。

实测同一个模型，同样的文本，真实 token 数是估算（UTF-8 字节 ÷ 4）的：

| 内容 | 真实 / 估算 |
|---|---|
| 随机十六进制 | 2.37 |
| 日志行 | 2.24 |
| JSON | 1.93 |
| 代码 | 1.23 |
| 英文散文 | 0.66 |
| 中文散文 | 0.71 |

按估算 9 万、接口实报 15.5 万，已超过配置的 11 万，火山没报错。

对话进行中不受影响：判断用上一轮的真实用量，只有「上一轮之后新增」的一小段靠估算。受影响的是没有真实用量的时刻：

1. 冷启动 / 重开旧会话的第一个请求：历史装多少全凭估算。
2. 一步里读进大块密集内容。

## Codex 的做法（本机 `~/Source/codex`，2026-09-26 版）

- 估算同样是字节 ÷ 4，源码自己注释为「粗略下界，不是精确计数」，没按内容类型校正。
- 压缩只看接口报的真实用量加「上次模型输出之后新增」的估算，达到窗口 90% 触发；发送前不用估算拦请求。
- 重开会话时恢复记在记录里的上次真实用量，不重估。
- 工具输出固定上限约 10KB（取头尾），与窗口大小无关。

结论：它没把估算做准，而是让估算出错的范围变小。我们照这个思路，不引入分词器。

## 决定

### A. 单次读入内容的上限定死（独立，可先做）

现状：`getTierOutputCap` 按窗口分档（≤32K：8192 / ≤128K：24576 / ≤512K：49152 / 更大：硬上限）。`exec` / `execute_command` 早已再与 16KB 取小，所以只有 `read_file`（及文档解析）能一次读进 24K 以上字符。

改成：上限 = min(原档位值, 16,000 字符)——大窗口不再多给，≤32K 的小窗口保持 8192 不变（固定 16,000 在小窗口里占比过高）。16,000 与 `exec` 现有的 16KB 对齐。压力系数（70% / 85%）和「剩余减预留」的收紧保留。行数档位不动。

依据：按实测，最密的内容约 0.6 token / 字符（哈希 0.59，中文 0.53），16,000 字符最坏约 1 万 token，在 110K 窗口里是一成不到。

取舍：大窗口模型单次少读一些，靠已有的分段读（起止行、末尾几行）补；`exec` 输出过大已落盘。不影响文件内容找回。

### B. 把真实用量存进记录，重开时直接用（等 cold-start 那一路合入后做）

照 Codex：每次接口返回真实用量时，那个数本来就在手上，把它（和当时的消息条数）随会话记录落盘；重开时恢复，和现有「上次响应之后新增的才估算」的口径接上。没有新概念，不算倍数。

- 重开时历史原样带回（有检查点接检查点，或装得下的原文）：第一个请求就以记下的真实用量为锚点，不再整段重估。
- 没有记录的老会话、全新会话：照旧，行为不变。
- 落盘：`AgentRecord` 新增两个可选数（上次真实用量、对应的消息条数），旧版本忽略，不需要迁移。
- 会推翻之前「不恢复用量记录」的决定。

已知缺口（不在这一步做）：重开时历史装不下、被裁剪过，消息和记下的用量对不上，这时锚点不能用，仍靠估算，由发送前拦截和紧急压缩兜底，第一个回复之后就有新锚点。这是少数情况，先不为它加东西；如果实际仍踩到，再单独讨论。

## 验收

- A：`scripts/probe-context-110k.js` 的「突然读进大文件」几项仍通过；`read_file` 在 110K 与 1M 窗口下单次返回上限相同。
- B：探测脚本新增一项——冷启动装密集历史（日志 / 哈希为主），第一个请求的接口实报不超过窗口；没倍数的老记录第一个请求后倍数被记下。
- 都要跑 `bash electron/cli/test-cli.sh --no-ai` 和相关单测。

## 明确不做

- 不引入分词器；不为每个模型硬编码系数。
- 不算偏差倍数，不按内容类型、关键词去猜密度。
- 不放松发送前拦截与三层兜底。
- 不改压缩触发线（目前约窗口的七成，已比 Codex 的 90% 保守）。
